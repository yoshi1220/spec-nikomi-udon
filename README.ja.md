# 仕様煮込みうどん

[English](README.md)

仕様煮込みうどんは、社内の開発標準や承認手続きに沿って、AI を使った仕様駆動開発（SDD）を取り入れるためのフレームワークです。

SIer や日本の伝統的な企業の開発チームを想定しています。たとえば、所定の書式で設計書を作るチームや、リリース前にテスト結果や承認記録を提出するチームです。新規開発と既存システムの改修の両方を対象とします。

## 開発の流れ

1. 仕様を詰めます。手元の要件から仕様のたたき台を作ります。一問ずつ確認し、対象範囲、期待する振る舞い、受け入れ条件をすり合わせます。
2. 実装計画を立てます。仕様を作業に分け、受け入れ条件ごとの確認方法を決めます。今回の要件に合う既存の実装方法を踏襲し、使えるコードは再利用します。
3. 実装して検証します。テストや手動確認で受け入れ条件を一つずつ確かめます。レビュー担当者が、何を確かめ、どの条件を満たしたかを追えるように結果を残します。

将来的には、レビューと承認を経た変更を現行仕様に反映し、次の改修で参照したり、社内書式の文書を作成したりできるようにします。

## 開発状況

初期版のスキルを[英語版](english/skills/)と[日本語版](japanese/skills/)で用意しました。まず、要件を詰めてから変更を検証するまでの流れを確かめます。

## 初期版の試し方

Git 2.23 以降と Python 3.8 以降を使えるプロジェクトに、どちらか一方の言語の `skills/` から6つのスキルのディレクトリをコピーします。配置先は、Codex では `.agents/skills/`、Claude Code では `.claude/skills/` です。`torikomu` が仕様作成の共通手順を参照できるように、6つとも同じ親ディレクトリに置きます。

導入先のプロジェクトでセッションを始めます。たとえば `nikomu` を使う場合、Codex では `$nikomu`、Claude Code では `/nikomu` と入力します。

システム全体の指針を作るには `shikomu`、何を変えるか相談するには `saguru` を使います。変更を起票するときは、要件やチケットなら `nikomu`、既存資料なら `torikomu` を使います。`nikomi.md` の内容を確認したら、`dandori` で実装計画を立て、`yonabe` で実装と検証を進めます。
