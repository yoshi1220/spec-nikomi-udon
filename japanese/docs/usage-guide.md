# 仕様煮込みうどん 利用ガイド

[English](../../english/docs/usage-guide.md)

新規案件では、システムの全体方針をまとめてから、最初の機能の仕様を決め、実装・検証します。既存案件では、現行コードをもとに設計書を起こし、その設計を根拠に最初の改修を進めます。どちらの案件でも、合意した仕様とテスト結果を残し、実装と設計書の更新を同じプルリクエスト（PR）でレビューします。

- [新規案件で最初の機能を作る](#新規案件で最初の機能を作る)
- [既存案件に導入して最初の変更を届ける](#既存案件に導入して最初の変更を届ける)
- [必要に応じて使うスキル](#必要に応じて使うスキル)

## 始める前に

このガイドの入力例は v0.0.7 の日本語版に対応します。ガイドは本体のリポジトリで読み、導入先の Git リポジトリではインストールしたスキルを使います。導入時に、アプリを実際に操作して一連の振る舞いを確かめる E2E テストの方式と、計画前の設計承認の有無を選びます。 [導入方法](../../README.ja.md#案件に導入する)

例の `$shikomi` などは、対象プロジェクトを開いた **Codex の会話欄**に入力します。Claude Code では先頭の `$` を `/` に置き換えます。各スキルが成果物を保存したら、その内容を確認して次の操作に進みます。続きから再開する場合は同じ作業ブランチを開くか、対象の変更用ディレクトリを示してください。

ここではメモアプリを例にします。作業は「メモを登録する」「タイトルで検索する」のように、利用者が確認できる単位のプロダクトバックログ項目（PBI）に分けます。

## 新規案件で最初の機能を作る

作業用のメモを保存し、一覧から見返せるアプリを作ります。最初の PBI は、タイトルと本文を登録し、一覧でタイトルを確認できるところまでです。

### 1. システムの全体方針をまとめる — `oukagai`

~~~text
$oukagai 作業メモを保存し、一覧から見返せるアプリを作りたいです。最初はメモの登録と一覧表示を扱います。
~~~

要件定義書がある場合は、`$oukagai --file <要件資料のパス>` で渡せます。スキルは資料や説明を読み、確認できる機能のまとまりや、機能・外部システム間の関係を整理します。技術上の未決事項は担当者と一問ずつ確認します。

| 成果物 | 入る内容 |
| --- | --- |
| `designs/system-overview.md` | システムの目的、範囲、主要機能、外部連携、共通の制約と根拠 |
| `designs/repository-structure.md` | プログラムを置くディレクトリと各ディレクトリの役割。配置が未定なら記入用のひな形 |
| `designs/technical-context.md` | 開発・検証・本番など、環境ごとの技術構成や採用判断。未確認の点や移行予定も記録 |

担当者は、最初に扱う機能や共通の制約を確認します。たとえば、一覧に表示するのは保存済みのメモで、検索や編集は後続 PBI にする、という方針を共有できます。次の工程では、この方針を参照して、一件目の仕様を具体化します。 [`oukagai` の手順](../skills/oukagai/SKILL.md)

### 2. 一件分の仕様と受け入れ条件を決める — `shikomi`

~~~text
$shikomi タイトルと本文を保存し、一覧にタイトルを表示します。タイトルが空の場合は入力を促し、保存しません。
~~~

スキルは新しい変更の作業ブランチと変更用ディレクトリを用意します。たとえば、`feature/001-create-note` と `specs/001-create-note/` です。変更用ディレクトリに仕様の初稿 `shikomi.md` と、成果物や進捗への案内をまとめる `oshinagaki.md`（お品書き）を作ります。

対話では「本文は空でもよいか」「空白だけのタイトルはどう扱うか」「再読み込みしてもタイトルが表示されることを確認するか」など、実装や合否を左右する点を一問ずつ詰めます。合意をその都度保存し、受け入れ条件に ID を付けます。たとえば次のように、操作と観測できる結果をセットで記録します。

| 条件 | 操作 | 確認できる結果 |
| --- | --- | --- |
| `AC-01` メモを登録できる | タイトル「定例会議」と本文を入力して保存し、一覧を再読み込みする | 「定例会議」が一覧に表示される |
| `AC-02` 空のタイトルでは登録できない | タイトルを空にし、本文を入力して保存する | タイトルの入力を促す表示が出て、一覧を再読み込みしても件数が増えない |

担当者は保存された仕様と受け入れ条件を読み、今回の変更として合意できるかを回答します。実装方法や合否を左右する未決事項が残る間は確認待ちです。たとえば空白だけのタイトルを受け付けるか決め切れなければ、次回も同じブランチで `$shikomi` を呼び、保存済みの仕様から再開できます。必要な判断がそろい、担当者が最終確認すると、仕様が確認済みになります。 [`shikomi` の手順](../skills/shikomi/SKILL.md)

### 3. 機能の基本設計書案を作る — `shitagaki`

~~~text
$shitagaki
~~~

スキルは保存済みの `shikomi.md`、全体方針、関連資料を読み、案件の書式で `shitagaki.md` を作成します。この例では、登録画面の入力項目、保存できる条件、保存後の一覧表示、入力エラー時の振る舞いを一つの機能の設計として読める形にします。利用者の手修正が入った仕様も、保存済みの内容を使います。

`structure-plan.json` には、変更理由、正本での設計書の配置先、更新する節や機能の関係を記録します。変更理由は改訂履歴に引き継がれます。画面項目定義書を有効にしていて、対象画面がある場合は `screen-items.md` も作ります。担当者は、受け入れ条件と設計に食い違いがないか、正常時と異常時の結果が読み取れるかを確認します。 [`shitagaki` の手順](../skills/shitagaki/SKILL.md)

**計画前の設計承認が必要な案件**では、この時点で案件所定の承認を得て、`osumitsuki` で記録します。既定の `none` では、設計案を確認したあと次の計画へ進めます。 [設計承認を記録する手順](#設計承認を記録する--osumitsuki)

### 4. 実装の順序とテストを決める — `dandori`

~~~text
$dandori
~~~

スキルは確認済みの `shikomi.md` と基本設計書案から作業を洗い出し、依存関係を有向グラフで検証します。たとえば「保存と入力チェックを実装する → 登録画面と一覧をつなぐ → 登録と入力エラーを確認する」のように、前提がそろう順に作業を並べます。

- `dandori.md` に、依存関係、実行順、作業ごとの完了条件、受け入れ条件ごとの確認方法を記録します。
- `e2e.md` に、テスト環境とデータ、操作手順、期待結果、対応する受け入れ条件 ID を記録します。画面撮影が有効なら、どの表示を確認した時点で撮影するかも指定します。

担当者は、各受け入れ条件に確認方法があるか、手順どおりに試せば意図した失敗を見分けられるかを確認します。たとえば `AC-02` は入力エラーの表示と、保存されていないことの両方を確認します。必要な前提がそろい、計画が実行可能になったら実装に進みます。 [`dandori` の手順](../skills/dandori/SKILL.md)

### 5. 計画に沿って実装し、進捗と検証を残す — `nikomu`

~~~text
$nikomu
~~~

スキルは `shikomi.md` と実行可能な `dandori.md` を照合し、前提のそろった作業からコードを実装します。この例では保存と入力チェック、登録画面、一覧表示を実装し、有効な入力の保存と空タイトルの拒否を確認します。作業の完了と、どの受け入れ条件がどの確認で合格したかを `dandori.md` に残すため、別のセッションからの再開にも使えます。

自動 E2E を使う場合は、この工程で `specs/<変更名>/e2e/` にテストを作成または更新し、実装中に実行します。すべての作業と受け入れ条件の確認がそろったら、完成した変更とテストを `ajimi` に引き継ぎます。 [`nikomu` の手順](../skills/nikomu/SKILL.md)

### 6. 完成した変更を E2E で試し、担当者が確認する — `ajimi`

~~~text
$ajimi
~~~

スキルは仕様と計画を照合し、計画が実行可能で、全作業が完了し、各受け入れ条件に有効な合格記録があることを確かめます。条件がそろったら、案件で設定した方式で `e2e.md` のシナリオを実施します。自動方式では同じ PBI のテストを再実行します。手動方式では担当者が手順を実施し、観測結果を渡します。たとえば「定例会議」を登録すると一覧に表示されることと、タイトルを空にするとメモを登録できないことを確かめます。

各ケースの実測値と合否を `e2e.md` に保存します。撮影が必要な場合は、今回の実行にひも付く `specs/<変更名>/evidence/<実行ID>/` 内の画像を結果から参照できます。実行が正常に終わり、必須項目がすべて合格したら、担当者が手順と結果を明示的に確認します。その確認も同じ `e2e.md` に記録されます。

不合格時は、実装やテストコードの問題なら `nikomu`、作業や確認方法の見直しが必要なら `dandori` に戻ります。復旧できれば一度再テストし、問題が残れば該当するケースと観測結果を示して担当者の判断を待ちます。前提が不足して試せない場合も、対象と不足している環境やデータを記録します。 [`ajimi` の手順](../skills/ajimi/SKILL.md) · [不合格からの復旧](../skills/ajimi/references/recover.md)

### 7. 正本の更新を用意して、実装と一緒にレビューする — `osameru`

~~~text
$osameru
~~~

スキルは `shikomi.md`、`shitagaki.md`、`e2e.md` の対応を照合します。現在の変更に対する必須 E2E の合格と担当者の確認を検証し、条件がそろえば、作業ブランチの `designs/specifications/` に設計書、現行構造、改訂履歴の更新を用意します。反映先は `oshinagaki.md` からたどれます。

担当者は PR で実装、設計書、テスト結果を照合します。PR がマージされると、共有ブランチでメモ登録機能の設計が正本になります。次の PBI では、その正本を根拠に現在の振る舞いを調べ、追加や変更が必要な範囲を判断できます。 [`osameru` の手順](../skills/osameru/SKILL.md) · [正本の構造と履歴](../skills/osameru/references/structure.md)

## 既存案件に導入して最初の変更を届ける

メモの登録と一覧表示がすでに動いているアプリに導入し、一覧にタイトルの部分一致検索を追加します。現行設計を確定する文書 PR と、検索を追加する改修 PR の二つに分けて進めます。

### 1. 現行の機能と技術構成を調べる — `okosu`

~~~text
$okosu 現行の機能一覧と技術構成を確認し、基本設計を起こしてください。最初の改修では一覧にタイトル検索を追加する予定です。
~~~

最初は現在のコミットを調べます。運用中の版を基準にしたい場合は、そのタグやコミットを指定します。スキルは対象版の画面、API、設定、実装、既存テストなどをたどり、確認できた機能と関係を `designs/system-overview.md` にまとめます。担当者が一覧を明示的に確認すると、その判断と調査した版が保存されます。同じ版を根拠に `designs/technical-context.md` を用意し、環境ごとの構成と残る確認事項も整理します。

既定では全体を対象に、根拠を確認できた範囲の基本設計を起こします。最初の改修に合わせて、本文を登録と一覧だけに絞ることもできます。その場合も確認済みの機能と関係は全体の構造に記録し、本文がまだない機能には整備状況を示します。調査対象の版と範囲を保存するため、中断後も同じ判断から再開できます。 [`okosu` の手順](../skills/okosu/SKILL.md)

### 2. 現行設計を文書 PR でレビューする

`okosu` は、対象機能の現在の振る舞いと根拠を `designs/specifications/` にまとめます。たとえば「一覧の初回表示には保存済みのメモが並ぶ」という記述を、対象版の実装と既存テストに照らし合わせます。コードや設定だけでは判断できない運用環境の動きは、未確認として残します。

同じディレクトリの `structure/` には機能の親子関係や依存関係を記したグラフと、固定 ID から設計書の節を引く索引を用意します。`history/` には ID ごとの改訂履歴などが入り、機能名や文書の置き場所が変わっても、その機能の改訂をたどれます。

担当者は、導入専用の文書 PR で調査した版、対象範囲、根拠、未確認事項を確認します。文書 PR での実動作の確認は任意です。マージした時点で共有ブランチの文書が正本になり、最初の改修で参照できます。 [調査・再開・文書レビューの手順](../skills/okosu/references/baseline.md)

### 3. 改修を起票して、追加する振る舞いと維持する振る舞いを決める

チケットの内容や会話で受け取った依頼から始める場合は、共有ブランチの正本を参照できる状態で `shikomi` を使います。

~~~text
$shikomi メモ一覧にタイトルの部分一致検索を追加します。検索欄が空の場合は、従来どおり一覧を表示してください。
~~~

要望書や変更依頼書などのファイルが主な入力なら、代わりに `torikomu` を使います。

~~~text
$torikomu requirements/note-search.md を主入力に、メモ検索の変更を起票してください。
~~~

`torikomu` は、指定ファイルを読んでから作業ブランチを用意し、根拠の位置を記した `shikomi.md` の初稿を作ります。たとえば要望書の本文では「タイトルを検索」、添付の表では「本文も検索」と読める場合は、両方の箇所と仕様への影響を示して担当者に確認します。その後は `shikomi` と同じ一問一答で仕様を詰め、最終確認まで進みます。 [`torikomu` の手順](../skills/torikomu/SKILL.md) · [`shikomi` の手順](../skills/shikomi/SKILL.md)

この例では、次のように新しい検索と、影響しうる既存の振る舞いを受け入れ条件にします。

| 確認すること | テストに使うデータと結果の例 |
| --- | --- |
| タイトルが部分一致するメモを表示する | 「会議」で検索すると、タイトルが「定例会議」のメモが表示される |
| 本文にだけ検索語があるメモを除く | タイトルが「週報」、本文だけに「会議」があるメモは検索結果に出ない |
| 検索欄を空にすると今までどおり一覧を表示する | 検索欄を空にすると、「定例会議」と「週報」が再び表示される |
| メモ登録と入力チェックを維持する | 新しいメモを登録でき、空タイトルを拒否する |

### 4. 既存の設計をもとに改修し、回帰を確認する

起票後は新規案件と同じスキルを使います。既存案件では、各工程で今回の追加と引き継ぐ振る舞いが両方記録されていることを確認します。

| 順序 | 操作 | メモ検索の例で得られるもの |
| --- | --- | --- |
| 1 | `$shitagaki` | 一覧の正本を参照し、検索欄・絞り込み・空欄時の動きを加えた設計案。登録や一覧に及ぶ影響と、正本の更新先も記録する |
| 2 | 承認を使う案件では、承認後に `$osumitsuki` | 現在の設計案に対する承認の記録 |
| 3 | `$dandori` | 検索の実装順と、検索、空欄時の一覧、既存の登録を確かめる計画と E2E テスト仕様 |
| 4 | `$nikomu` | 検索の実装と作業記録。既存テストや追加したテストで、登録と一覧への影響も確認する |
| 5 | `$ajimi` | 完成したアプリで操作した結果と、担当者の確認 |
| 6 | `$osameru` | 作業ブランチ上の設計書と改訂履歴の更新。改修 PR のマージ後、検索を含む現行設計が正本になる |

たとえば入力欄を空に戻しても一覧が絞り込まれたままなら、`ajimi` の観測結果をもとに、合意済みの仕様と計画でそのケースを扱えているかを確かめます。計画に沿えば直せる場合は `nikomu` で修正し、その後に再テストします。 [既存案件にも共通する手順](#3-機能の基本設計書案を作る--shitagaki)

## 必要に応じて使うスキル

### 課題や取り組む範囲を探る — `saguru`

~~~text
$saguru 保存したメモが見つからないという相談があります。誰がどんな場面で困っているかから整理してください。
~~~

具体的な場面をもとに、困っている人、問題が起こる条件、改善できたと言える基準を一問ずつ整理します。たとえば、最近のメモを探せないのか、昔のメモをキーワードで探せないのかで、先に取り組む範囲が変わります。合意した課題と方針、保留事項は会話に残せます。ファイルに保存する場合の推奨先は `saguri/<相談名>/saguri.md` です。この場所から起票するには `shikomi` にパスを渡します。対応する作業ブランチの `specs/<変更名>/saguri.md` は `shikomi` が自動で参照します。 [`saguru` の手順](../skills/saguru/SKILL.md)

### 設計承認を記録する — `osumitsuki`

設計承認は、基本設計書案の確認後、実装計画の前に行います。案件の設定に応じて次のように進めます。

| 設定 | 担当者の操作と記録 |
| --- | --- |
| `none`（既定） | 仕様と設計案を確認し、計画へ進む |
| `operational` | 案件所定の承認を得たあと、たとえば `$osumitsuki 2026-11-20 に設計責任者が承認` と伝える。実際の承認日と承認者がお品書きに記録される |
| `pr` | 設計案が PR で承認されたあと `$osumitsuki` を実行する。承認時と現在の版を照合し、有効な承認をお品書きに記録する |

設計承認を使う案件で再設計に着手すると、通常の承認は承認待ちに戻り、既存の計画は作業記録を残して保留になります。更新した設計案を承認・記録してから、計画の再確認に進みます。案件所定の了承を得た緊急対応では、たとえば `$dandori --emergency 本番障害の復旧を優先` と伝えると、理由がその PBI に保存されます。 [`osumitsuki` の手順](../skills/osumitsuki/SKILL.md) · [計画前の設計承認](../../README.ja.md#計画前の設計承認)

### 設計書を新しい書式にまとめて移す — `koromogae`

~~~text
$koromogae メモ機能の基本設計書を案件の新しい書式に揃えてください。
~~~

チームで `designs/basic-design.template.md` の書式を決めたあと、既存の機能別基本設計書をまとめて移したいときに使います。スキルは業務ルール、振る舞い、根拠、手修正、節の固定 ID を新しい欄へ引き継ぎ、書式移行専用の文書 PR の差分を用意します。担当者は、見出しの移動前後で設計上の意味が保たれているか、新設の欄で追加確認が必要な点が分かるかを確認します。 [`koromogae` の手順](../skills/koromogae/SKILL.md)

### システム全体の E2E を作る — `moritsuke`

~~~text
$moritsuke
~~~

正本をもとに、変更を取り込んだあとも繰り返し確かめたい業務の流れを、ルートの `e2e/` にテストシナリオとしてまとめます。たとえば「メモを登録し、一覧の検索欄でそのメモを見つける」流れでは、登録したメモを同じタイトルで探し、結果に表示されるところまでを確認します。スキルは既存のケースで期待結果を検証できるか調べ、不足するケースを追加します。期待結果が変わった場合は、正本に合わせて更新します。

シナリオ、手順、期待結果、対象テスト、必要な環境を記録します。既存のシナリオ形式がなければ `e2e/scenarios.md` を用います。自動方式ならテストコードもルート `e2e/` に置きます。 [`moritsuke` の手順](../skills/moritsuke/SKILL.md)

### システム全体の E2E を実行する — `shishoku`

~~~text
$shishoku メモ検索
~~~

指定した機能、シナリオ ID、ファイルなどに該当するルート E2E を実行します。指定なしの `$shishoku` はルートの全件を対象にします。実行の範囲、環境、各シナリオの実測結果と合否を、既定では `evidence/system/<実行ID>/results.md` に記録します。画面証跡が必要な場合は、その実行で保存した画像も参照できます。

PBI の `ajimi` は一件の変更の受け入れ確認を担当し、その結果を PBI の `e2e.md` に記録します。ルートの `shishoku` は現行の正本に沿って、機能をまたぐ業務の流れを繰り返し検証するときに使います。 [`shishoku` の手順](../skills/shishoku/SKILL.md)

### E2E テストを書くときの共通ルールを使う — `e2e-authoring`

PBI のテストを用意する `nikomu` と、ルートのテストを用意する `moritsuke` が参照するスキルです。チームで E2E テストを直接編集するときも使えます。ケース ID を付け、操作後に今回のデータや期待するエラーが画面に現れるまで確認するアサーションを入れます。撮影が有効な場合は、指定した表示を確認した直後に画像を保存し、今回の実行・ケース・場面と結び付けます。たとえば登録後の一覧では、今回登録したタイトルが見えることを確かめてから撮影します。 [`e2e-authoring` の手順](../skills/e2e-authoring/SKILL.md)
