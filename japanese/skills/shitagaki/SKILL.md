# 基本設計書を下書きする

利用者が指定した `specs/<変更名>/` を使います。指定がなければ、現在の `feature/<変更名>` ブランチに対応する変更用ディレクトリを選びます。対象を特定できなければ利用者に確認します。まず `shikomi.md` を読みます。見つからない場合は必要なパスを示し、ファイルを作成する前に終了します。手で修正された内容も含め、実行時点で保存されている本文を使います。

設計の作成・やり直しに着手するときは、[お品書きの準備・移行手順](../osumitsuki/references/index.md) に従い、そのあと同じスクリプトの `redraft` を実行してから設計作業を始めます。承認済みはその場で承認待ちに戻り、途中で中断しても旧承認で計画に進みません。緊急対応は同じPBIの状態と理由を引き継ぎます。承認が有効か、お品書きに以前の承認欄が残っていれば、`redraft` は既存の計画も保留にし、作業項目と結果を再計画に引き継ぎます。

1. 対象機能と変更後の振る舞いを把握します。システム全体の指針、関連資料、既存の正本を読みます。`dandori.md`、実装コード、確認結果も、あるものをそれぞれ照合します。変更前の現行実装と予定された変更後の仕様を区別します。同じ時点の振る舞いについて食い違う場合は、根拠を示して利用者に一問ずつ確認し、作成・更新を待ちます。
2. 正本がない既存機能では、対象機能全体の現行の振る舞いを調べます。維持する振る舞いと変更後の振る舞いをまとめます。既存の正本がある場合は、その内容を基に更新後の文書を作ります。根拠が足りない項目は「未確認（利用者の確認が必要）」とし、確認内容と影響を示します。新しい正本のパスはシステムの機能構成に合わせます。
   複数の機能が変更対象の契約を使う場合は、[一時 GraphML の操作](../dandori/references/work-graph.md)で、契約から利用機能へ `consumed_by` の辺を張る。根拠の箇所を辺に付け、`affected FILE 契約ID --via consumed_by` の各候補について、どの設計案の入出力・異常時の振る舞いを変える必要があるかを照合する。
3. [案件の基本設計書式と作成方針](references/basic-design-format.md) を読み、機能別の本文書式を使い、対象機能の案を `shitagaki.md` に保存します。[正本への受け渡し形式](../osameru/references/format.md) に従い、機能ごとの文書とその反映先を記録します。実行時は導入先の設定を読み、画面項目定義書が有効で対象画面がある場合は、同じ変更用ディレクトリに `screen-items.md` も作ります。画面項目定義書には、画面、項目名、入出力、入力制約、表示や編集の条件など、根拠のある情報を記します。
4. 再実行では現行の `shitagaki.md` を読み、影響を受ける箇所を更新します。前提から変わった仕様は、必要に応じて構成から見直します。有効な手修正とレビューの反映内容を引き継ぎます。正本が途中で更新されていた場合は、最新の正本と照合し、本文に反映してから参照する版を更新します。
5. 目的・対象範囲、業務ルール、入出力、正常時・異常時の振る舞いを確認します。該当する権限や外部連携を含め、主要なケースの前提、操作、観測できる結果からテストの期待結果が分かることを確かめます。参照元も記します。先に用意した `oshinagaki.md` の基本設計書案の行を更新します。設計案の場所と確認待ちの項目を伝えます。正本への反映は `osameru` で行います。

`shitagaki.md` の変更を保存したら、引き継ぎ前にもう一度 `redraft` を実行します。編集中に旧版の承認が記録された場合も承認待ちに戻り、緊急対応は引き継がれます。お品書きが承認待ちなら、案件の手続きまたはPRで承認を得たあと [osumitsuki](../osumitsuki/SKILL.md) で記録して `dandori` へ進みます。承認が無効または緊急対応なら、設計案の作成後に `dandori` を案内します。

利用者への確認は一問ずつ進めます。方針が複数あるときは推奨順に番号を付け、自由入力も受け付けます。
