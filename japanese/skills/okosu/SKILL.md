# 既存案件の現行設計を起こす

既存の Git リポジトリで、最初の改修が参照する現行設計を用意する。[調査・再開・文書レビューの手順](references/baseline.md) に従い、調査対象のコードの版を確定し、既存の全体指針と設計書を読む。

1. [全体指針のテンプレート](../oukagai/assets/system-overview.template.md) を使い、システム全体の機能一覧と関係を `designs/system-overview.md` にまとめる。判断に影響する不明点を示し、利用者が一覧全体を対話で確認できるようにする。範囲の判断に影響する不明点が解消し、利用者が一覧を明示的に確認した時点で、その状態と調査対象の版を同じ文書に保存する。
   同じ調査対象の版を使い、[技術構成の手順](../oukagai/references/technical-context.md)に従って `designs/technical-context.md` を用意する。確認できた情報を先に記入し、全体指針からリンクする。見出し順に対話で残件を確認し、技術構成の差分と未確認事項も導入時の文書レビューに含める。
2. 既定では現状全体を対象とする。設計書がなくても、調査版のメニュー・画面・API・定期処理・外部連携の入口から、実装・設定・テストをたどる。確認できた全機能について根拠のある範囲まで本文を整備する。利用者が本文の範囲を指定した場合も、グラフには確認済みの全機能と関係を載せ、本文が未整備の機能はその状態を示す。調査版と整備範囲を保存する。
3. [案件の基本設計書式と作成方針](../shitagaki/references/basic-design-format.md) を読み、機能別の本文書式を使い、対象機能の **現行の** 基本設計書を `designs/specifications/` に用意する。対象版のコード・設定・既存テストで説明を照合し、根拠と未確認事項を記録する。利用者が本文の範囲を限定した場合は、対象機能と予定する改修の関係を記す。
   [正本の構造管理](../osameru/references/structure.md)に従い、初期構造の計画、本文の固定ID、既存履歴の移行を用意する。差分をプレビューし、文書ブランチで反映して `structure-check` で確認する。既存の改訂履歴がない機能は調査コミットを初回記録にする。
4. 導入専用の文書 PR でレビューできるよう、対象版、範囲、文書の差分、残る未確認事項を提示する。実動作の確認は文書 PR の必須条件に含めない。PR をマージした時点で基本設計書を正本とし、共有ブランチの正本を参照して最初の変更を `shikomi` または `torikomu` で起票する。PR の送信やマージは利用者の依頼を受けて行う。

再開時は全体指針にある調査対象の版、確認状態、選択範囲を読み、現在も有効な判断を引き継ぐ。不明点は影響が大きいものから一問ずつ確認する。具体的な案がある場合は推奨理由と自由入力を添える。
