# 既存案件の現行設計を起こす

既存の Git リポジトリで、最初の改修が参照する現行設計を用意する。[調査・再開・文書レビューの手順](references/baseline.md) に従い、調査対象のコードの版を確定し、既存の全体指針と設計書を読む。

1. [全体指針のテンプレート](../shikomu/assets/system-overview.template.md) を使い、システム全体の機能一覧と関係を `designs/system-overview.md` にまとめる。判断に影響する不明点を示し、利用者が一覧全体を対話で確認できるようにする。範囲の判断に影響する不明点が解消し、利用者が一覧を明示的に確認した時点で、その状態と調査対象の版を同じ文書に保存する。
2. 確認済みの一覧を示し、**改修対象と影響する機能**か、**システム全体**かを聞く。変更の入口と影響する機能が分かる場合は前者を推奨し、導入時に全機能の基本設計書が必要な場合は後者を推奨する。案は推奨順に番号を付けて理由を添え、自由入力も受け付ける。前者では起点となる改修の説明から対象機能と影響先をたどり、必要な判断を一問ずつ確認する。選んだ範囲と対象の機能を全体指針へ保存してから基本設計書を作る。
3. [基本設計書案テンプレート](../shitagaki/assets/shitagaki.template.md) の機能別本文を使い、選んだ機能の **現行の** 基本設計書を `designs/specifications/` に用意する。対象版のコード・設定・既存テストで説明を照合し、根拠と未確認事項を記録する。今後の改修案が入力にある場合は、整備範囲を決める材料として使う。
4. 導入専用の文書 PR でレビューできるよう、対象版、範囲、文書の差分、残る未確認事項を提示する。実動作の確認は文書 PR の必須条件に含めない。PR をマージした時点で基本設計書を正本とし、共有ブランチの正本を参照して最初の変更を `nikomu` または `torikomu` で起票する。PR の送信やマージは利用者の依頼を受けて行う。

再開時は全体指針にある調査対象の版、確認状態、選択範囲を読み、現在も有効な判断を引き継ぐ。不明点は影響が大きいものから一問ずつ確認する。具体的な案がある場合は推奨理由と自由入力を添える。
