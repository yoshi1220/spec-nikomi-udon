# 一つの場面から論点を組み立てる

利用者が最初に挙げた機能は解決案の候補として扱う。実例があれば、直近の一件で期待と実際が分かれた箇所を追う。新しい業務などで実例がまだなければ、想定する利用者と場面を一つ取り上げる。利用者が決めた目標と、実際の利用で確かめる仮説を分けて記録する。資料や会話で分かっていることを起点にし、次の観点のうち、方針の選択に効くものを使う。

| 観点 | 確かめること |
| --- | --- |
| 誰が、いつ困るか | 作業する人と結果を受け取る人、そのときの目的、困らずに済んだ似た場面との違い。 |
| 今どうしているか | 直前に起きたこと、本人が見た結果、回避策とその負担。観測した事実と、原因についての推測を分ける。 |
| 何に取り組む価値があるか | 困る頻度や影響、現状を維持した場合の負担。数値がなくても、具体的な一件から何が言えるかを確かめる。 |
| 何が変わればよいか | 同じ場面で誰がどんな違いを観測できれば改善か。維持する制約、優先する対象、今回外す範囲。 |
| どの方向なら効くか | それぞれの案がどの原因に働くか、効果が出ない条件、別の人に移る負担。現状の運用で解消できる案も、成立する場合は比較する。 |

目的の下に論点を分け、各論点に根拠（資料の箇所や利用者の実例）、未確認の点、答えによって変わる判断を対応させる。「先に確かめること → それに依存する判断」をたどる。同じ前提を使う複数の案はまとめて見直せるようにする。手元で検証できる事実は調べてから聞く。方針に影響しない実装の詳細は、後続の仕様化で扱える。

たとえば「申請にリマインダーがほしい」と言われたら、最初の一問は「直近で申請が止まったとき、何が起きていましたか？」でよい。「担当者は気づいていたが、代理承認できなかった」という答えなら、通知不足という仮説を見直す。次に、代理承認が必要だった場面に共通する条件を確かめる。通知時刻の選択は、その答えで作業が進む根拠が出てから扱う。
