# E2E テスト仕様書に沿って確認する

## 開始条件を確認する

`shikomi.md`、`dandori.md`、`e2e.md` を読み、合意済みの仕様、計画、テストの手順と期待結果が対応していることを確かめます。計画の状態マーカーがある場合は、先頭の `<!-- dandori-plan: ready -->` 一つだけを有効とします。マーカーのない旧形式では計画の内容を照合します。いずれも全作業のチェックと全受け入れ条件に対する現在有効な合格の記録が必要です。不足や食い違いがあれば、該当箇所と次に行う工程を伝えます。

新しい実行 ID を発行する前に、設定した方式で対象の振る舞いを実施し、期待結果を判定できるか確認します。準備が必要な場合は対象の ID と不足条件を伝え、次の手順を案内します。

自動テストコードを使う方式では、`dandori.md` のコマンドが今回の PBI の `specs/<変更名>/e2e/` だけを選び、`e2e.md` の振る舞い ID を網羅することを確認します。旧配置のテストを引き継ぐ場合やケース・コマンドが足りない場合は、該当 ID を `nikomu` に渡します。

- **Playwright**。案件のランナーとブラウザを準備します。同じ版の `init` を再実行すると Chromium の起動とアサーションを確認できます。
- **エージェントのブラウザ操作**。Codex デスクトップの内蔵ブラウザ、または Claude Code の `/chrome` でテスト対象を開き、アクセス権と期待値の確認方法を確かめます。
- **Chrome 拡張**。案件の拡張を有効にし、対象サイトへのアクセスとアサーションの実行を確認します。
- **手動テスト**。担当者にテスト環境・データ・手順を渡し、各 ID の観測結果と合否を記録できることを確かめます。

利用者が方式変更を選んだ場合は `python3 <osameru.py> setup --method <方式>` で案件設定を変更します。前回の結果は元の実行 ID に対応づけ、準備が整ってから新しい実行を始めます。

## テストを実施して結果を記録する

1. [設定と記録の手順](../../osameru/references/format.md) に従い、プロジェクトで設定したテスト方法を使います。新しい実行を始める場合は、環境、データ、ツールを用意し、実施の直前に `start-e2e` を実行して実行 ID を控えます。用意できない前提があれば、未実施の振る舞い ID と不足しているものを記録して伝えます。`oshinagaki.md` があれば、E2E の実施・確認・復旧の状況を成果物欄に反映します。
2. 実施済みの結果を後から受け取る場合や、中断や確認待ちから続ける場合は、対象の実行 ID を `e2e.md` の `e2e-run` と照合します。その実行 ID で `check-e2e-run --tested <実行ID>` を使い、テスト時の入力が現在も有効であることを確認します。結果を記録済みであれば、残っているテストまたは結果の判定から続けます。
3. キャプチャが有効で取得場面がある場合は、現在の PBI の `evidence/<実行ID>/` を用意する。自動テストには `dandori.md` の受け渡し方法（標準は `NIKOMI_E2E_EVIDENCE_DIR` に絶対パス）で今回の保存先を渡す。撮影が無効、または実行するケースに取得場面がなければ、撮影用の設定を外す。[撮影条件](../../e2e-authoring/SKILL.md) に従い、各場面で期待する表示を確認してから保存し、今回の試行で保存した画像を該当 ID にリンクする。複数場面を列挙した行では、仕様書の各場面名を証跡のリンク名に使う。必要な画像を保存できなければ理由を記し、確認待ちとする。

   選んだ方法でテストし、観測結果と判定を振る舞い ID ごとに集めます。
   - **エージェントのブラウザ操作**。Codex デスクトップの内蔵ブラウザまたは Claude Code の公式 Chrome 連携で指定の画面を操作し、各 ID の期待値と観測値を照合する。指定された場面の証跡を保存する。
   - **Playwright**。`nikomu` から引き継いだコマンドで現在の PBI のテストを再実行し、今回の実行で確認できた観測結果と判定を ID ごとに記録します。収集漏れやスキップがあれば、該当 ID は未実施とします。実施欄にコマンド全体の終了結果も記録します。全ケースのアサーションが成功しても後処理などでコマンドが失敗した場合は、実施欄にエラーを残します。各ケースの観測結果を保持し、影響する項目（特定できなければ今回の全項目）の判定を未確認にします。
   - **Chrome 拡張**。利用できるプロジェクトの Chrome 拡張で、指定されたブラウザー、画面、データに対し各手順を実施します。期待する文言、値、状態などを拡張のアサーションや評価結果から自動で確かめます。画面を操作した記録と、期待結果を満たした判定を区別します。アサーションを実行できないケースは必要な機能を示し、未確認として記録します。
   - **手動テスト**。担当者に仕様書の手順を案内し、各 ID の観測結果と合否を受け取って記録します。
4. 結果を保存する前にも `check-e2e-run` で実行 ID と入力を確認します。照合に失敗したら、理由と影響する ID を伝えます。入力が変わった通常の実行は、現行の入力で始め直します。復旧中の再テストでやり直しが必要になった場合は、利用者の対応待ちとして記録します。
5. `e2e.md` には、期待と異なる観測結果は `NG`、期待どおりで今回必要な全場面の画像もそろった場合は `OK` と記録します。期待値は確認できても必要な画像が欠けた場合は、観測値を残して判定を未確認にします。未実施・未確認の項目には理由を記します。テスト方法、環境、実施日も記録します。`e2e:execution` 欄がある場合はその中に記入します。キャプチャが有効で指定された場面があれば画像を PBI 内の `evidence/<実行ID>/` に置き、対応する行にリンクします。
6. 復旧中の再テストは、[復旧手順の完了判定](recover.md#一度だけ復旧して再テストする) に結果を返します。通常の実行では、コマンドの異常終了や項目の不合格があれば [復旧手順](recover.md) へ、必須項目がすべて合格していれば担当者の確認へ進みます。未実施や未確認だけが残る場合は、該当 ID と残る前提を伝えます。

## 担当者の確認を記録する

実行が正常に完了し、必須項目がすべて `OK` の場合は、`check-e2e-run` が成功してから、実施した手順と各 ID の判定を担当者に提示します。担当者が実施内容と結果を明示的に確認したら、実行 ID と確認者名を指定して `review-e2e` を実行します。確認がすでに記録されていれば、その記録を使います。完了を報告する前に `verify-e2e` を実行します。CLI が照合に失敗した場合は、その理由と残る確認を伝えます。入力の変更により復旧中の再テストをやり直す必要があれば、利用者の対応待ちとして記録します。
