# E2E テストの不合格から復旧する

## 復旧を再開する

- 対応待ちの場合は、利用者の判断や対応を確認する。再テストの開始前に止まっていた場合は、前提がそろってから記録済みの工程を続ける。再テストを終えた後の対応待ちでは、利用者が次の実行を求めた時点で復旧記録を閉じ、通常の実行として開始する。
- 進行中の場合は、記録済みの工程から続ける。再テストの開始まで進んでいれば手順 3 へ、結果を記録済みなら手順 4 へ、担当者の確認待ちなら [確認の手順](run-e2e.md#担当者の確認を記録する) へ進む。

## 次に行う工程を決める

`e2e.md` に記録した現行の実行結果を使う。該当する振る舞い ID の期待結果と観測結果を、合意済みの `shikomi.md`、`dandori.md`、現行の実装と照合する。同じ計画を正しく実行すれば仕様を満たせるかを確かめ、次の工程を決める。

| 確認できた原因 | 次に行うこと |
| --- | --- |
| 仕様と計画は妥当で、実装が計画どおりの振る舞いを満たしていない | [nikomu](../../nikomu/SKILL.md) で影響する作業と受け入れ条件を見直し、修正・検証する。 |
| 合意済みの仕様を満たすには、作業、前提、確認方法、E2E テスト仕様のいずれかを変える必要がある | [dandori](../../dandori/SKILL.md) で計画を更新する。実行可能になったら [nikomu](../../nikomu/SKILL.md) で影響する作業を実施・検証する。計画と実装の両方に問題があれば、計画から始める。 |
| テスト環境、データ、ツール、またはテストコードに問題がある | 利用できる範囲でテストの準備を直す。利用者の対応が必要な場合は、不足している前提と影響する ID を伝える。 |
| 仕様の合意が不足している、または原因を特定する根拠が足りない | 「未確認（利用者の確認が必要）」と記録し、該当箇所と確認してほしいことを伝える。仕様を詰め直す場合は `shikomi` を案内する。 |

## 一度だけ復旧して再テストする

1. 復旧を始める前に、元の実行の `evidence/<実行ID>/recovery.md` に、実行 ID、該当 ID と結果、証跡への参照、原因の根拠、選んだ工程、現在の段階を記録する。再計画や `start-e2e` で結果欄が更新された後も、この記録を引き継ぐ。`oshinagaki.md` があれば、E2E の状況欄から復旧記録を参照できるようにする。
2. 同じ変更用ディレクトリに対して、選んだ工程を順に実行する。`dandori` や `nikomu` には、該当 ID、期待結果、観測結果と根拠を渡す。次の工程に進む前に完了を記録する。前提が足りなければ、現在の工程と残件を記録して利用者の対応を待つ。
3. 必要な工程が完了したら [テストの開始条件](run-e2e.md#開始条件を確認する) を照合する。テストコードと環境を用意してから、開始時点の `e2e-run` の ID（なければ「なし」）を復旧記録に保存し、`start-e2e` を実行する。返された新しい ID を復旧記録に控え、その実行として [テスト手順](run-e2e.md#テストを実施して結果を記録する) に従い必須項目を再テストする。新しい ID を控える前に中断した場合は、開始前の記録と `e2e.md` を照合する。開始前のままなら `start-e2e` から進み、再テストの ID が発行済みならその ID を引き継ぐ。結果を後から受け取る場合も同じ ID を使う。再テストを特定できない場合や入力が変わってやり直しが必要な場合は、利用者に状況を伝えて対応待ちにする。
4. 必須項目がすべて合格したら確認待ちを記録し、担当者の確認に進む。`verify-e2e` が成功したら復旧の完了を記録する。再テストを終えても不合格や未実施・未確認が残る場合は、元の実行と再テストの結果、試した対応、残る ID、利用者に判断または対応してほしいことを説明する。復旧記録を利用者の対応待ちに更新し、自動での復旧はここで止める。
