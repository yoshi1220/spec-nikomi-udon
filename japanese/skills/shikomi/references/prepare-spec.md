# たたき台を用意する

## 入力と作業先を確かめる

1. 利用者がまとめのパスを指定したら、ブランチを切り替える前にそのファイルを読む。読み取れない場合は正しいパスか本文を求める。`torikomu` からこの手順を使う場合は、そこで指定された資料を主入力とする。
2. [案件ディレクトリを用意する手順](change-directory.md) で対象のブランチと作業ツリーを特定する。既存案件ならそのディレクトリを使い、新規なら採番して `specs/<変更名>/` を用意する。
3. `shikomi` でまとめのパスが未指定のときだけ、対象の作業ツリーで `specs/<変更名>/saguri.md` を確認する。あれば読み、なければ今回の依頼・PBI・この案件についての会話から進める。リポジトリ直下の `saguri/` は探索しない。

まとめを使った場合は、課題・範囲・採用した方針と理由を初稿に引き継ぎ、元のパスを参照元に記す。未検証の仮説や追加調査は未決事項に、見送った案はその理由とともに対象外に記す。この案件について利用者が会話で訂正した点は、最新の合意を使う。再開時は既存の `shikomi.md` を読み、まとめと食い違う判断は、双方の根拠と今回の依頼を照合して確認する。

## 分かっている情報でたたき台を書く

新規の `shikomi.md` は [仕様のテンプレート](../assets/shikomi.template.md) を使う。先頭の `<!-- shikomi-review: pending -->` を残し、分かっている内容で次の４項目を記入する。

- **目的・対象範囲**。変更する理由と、今回扱う範囲を記す。
- **期待する振る舞い**。利用者の操作や入力と、外から確認できる結果を書く。
- **合意した設計上の判断**。確認済みの判断と理由を残す。プロジェクトの全体指針、既存の正本、類似実装に該当する制約があれば参照する。
- **受け入れ条件**。前提・操作・観測できる結果を書く。条件ごとに重複しない `AC-01` 形式の ID を付け、一度付けた ID は振り直さない。

参照元を記す。今回の変更に関わる不明点や食い違いは、[決定の記録と検証](record-decisions.md) の「未決事項の記録」に従って初稿に残す。情報が足りない分類や関係、未合意の振る舞いを確定事項として書かない。受け入れ条件に必要な前提や結果が未確認なら、その不足を記し、値や振る舞いを補わない。既存改修では、現在観測できる振る舞いと、維持すると合意した仕様を区別する。

「元の依頼」には、利用者の言葉で求められた機能・制約・対象外を残す。既存資料が主入力なら、資料が示す目標を該当箇所への参照とともに記す。

既存の仕様に「元の依頼」がなければ、参照できる元の入力から目標を確認する。入力が見つからない場合は、記載済みの目的・対象範囲・合意済みの要件を起点にする。既存の見出しと ID を保つ。既存要件の意図が分からなければ、調査する論点として扱う。

## 面談を始める

新しい `shikomi.md` の初回保存後に [お品書きの準備手順](../../osumitsuki/references/index.md) の `init` を実行し、案件設定に沿った `oshinagaki.md` を用意する。既存PBIは次の設計・承認・計画時に同手順で移行する。

たたき台を保存したら、必ず [明確化の手順](clarify-spec.md) に進む。再開時には、既存の仕様とそこで確定した判断を読んでから、面談の状態を組み直す。
