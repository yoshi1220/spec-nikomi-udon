# 単体テストの計画と実施

## 確認する要件を決める

1. `shikomi.md`、基本設計書案があればその内容、既存コードとテストを照合する。変更する振る舞いと影響を受ける振る舞いのうち、関数やクラスなどの単体で確かめられる規則を洗い出す。たとえば入力の境界、禁止される状態遷移、戻り値、失敗時に副作用が起きないことを確認する。外部サービスとの接続や画面を通した操作が必要な条件は、結合テストや E2E で確認する。
2. `dandori.md` の「単体テスト」に、規則の出典、対象の単体、前提と入力、観測する結果、テストの名前または対象ファイルを記す。出典には受け入れ条件 ID か仕様・設計の該当箇所を使う。単体で確かめる規則ごとに、その規則に違反した場合にアサーションが失敗するケースを用意する。既存テストを使う場合は、現在のアサーションで該当する規則を確かめられることを示す。
3. 新規・変更した振る舞いには、対応する単体テストコードの追加または更新を計画に含める。関連する作業の中で、テストの準備、実装前の失敗確認、実装、同じテストの合格確認の順を記す。一つの作業の中で順に進めてもよい。すでに確認できる挙動を保つ変更では有効な既存テストを使い、確認できない規則のテストを補う。文書だけの変更など、対象となる実行可能な振る舞いがなければ、その理由を記録する。
4. 案件の既存のランナーと計測方法を使い、対象のテストを選ぶコマンドと計測範囲を記す。初期構築などでランナーがなければ、案件の技術構成に合うランナーとカバレッジ計測の準備を計画する。

## 実装前後に同じテストを使う

1. `nikomu` は仕様に沿った単体テストコードを先に書く。対象の規則を破っている実装で、意図したアサーションが失敗することを確認する。ビルドエラー、環境不備、テスト未収集はこの失敗に数えない。既存の振る舞いを保持するだけなら、先に既存テストの合格を確認する。途中実装から再開して変更前に戻せない場合は、利用者の編集を保ち、隔離した作業場所で変更前の版か対象の規則だけを破る一時的な変更を使う。検出を確かめられない場合は理由を残し、確認済みにしない。
2. [単体テストの実行ヘルパー](../../nikomu/scripts/unit_test.py) に案件のコマンドを渡す。`--expect-output` には失敗時は対象のアサーションに固有の出力、合格時は対象ケースが実行され合格したことが分かる出力を指定する。失敗を表す終了コードの既定値は 1 とする。ランナーがアサーションの失敗に別のコードを使う場合は、`red` に `--failure-exit <コード>` を指定する。実際のログで対象ケースと結果を確かめる。

   ```text
   python3 <unit_test.py> red --expect-output "<対象のアサーションの失敗メッセージ>" -- <ランナーと引数>
   python3 <unit_test.py> green --expect-output "<対象のテストの合格を示す出力>" -- <同じケースを選択するランナーと引数>
   ```

3. 規則を満たす実装に変えたら同じケースと影響範囲の単体テストを実行する。成功件数とスキップを確かめ、失敗・合格のコマンド、実際の結果、テストへの参照を `dandori.md` に残す。アサーションは、要件から求めた値・状態・副作用を確認する。呼び出しただけのテストや、常に成立するアサーションは取り除く。単体で確かめる条件が未実施または不合格なら、実装完了にしない。

## 行カバレッジの目標は 80% 以上

単体テストだけを実行して、対象の本番コードの行カバレッジを測る。既存案件では今回追加・変更する実行可能な振る舞いを含むモジュール、新規案件では今回作る本番モジュールを対象にする。テストから一度も読み込まれない対象ファイルも計測に含める。テストコードや変更に関係しないモジュールを分母に足したり、既存の除外設定を根拠なく広げたりしない。

`dandori.md` に対象範囲、計測コマンド、行カバレッジの実測値、レポートで確認する場所を残す。80% 未満なら未検証の行を要件に照らし、確認できていない規則のテストを補ってから測り直す。残る未計測・未達は理由とともに報告する。合否は要件に対応する単体テストの結果と案件所定の基準で判断する。
