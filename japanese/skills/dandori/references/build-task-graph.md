# 変更対象、作業、依存関係を洗い出す

## 仕様と既存実装を照合する

1. `shikomi.md` から期待する振る舞い、合意した設計判断と制約、受け入れ条件を拾う。条件ごとに、どの前提で何を行い、何を観測すれば満たしたと分かるかを確認する。条件 ID は仕様書の表記を使う。
2. 関連する全体指針、正本、コード、テストを読む。変更が通る既存の入口、制約を適用する箇所、再利用できる処理と確認手段を特定する。既存の方法が要件に合えば踏襲する。異なる方法を採るなら、必要な理由を記録する。
3. 各条件について、追加・変更すべき部分と、既存の振る舞いを確認すればよい部分を見分ける。判断が仕様の変更を伴う場合は明確化に戻る。技術的な前提が不明なら既存実装やテストで確かめる。調査の結果により計画自体を決め直す必要がある場合は、調査対象と計画を再開できる条件を示す。

技術構成が実装方針や検証条件を左右する場合は、`designs/technical-context.md` があれば該当節で対象環境の現行構成と採用決定済みの移行先を照合する。計画では根拠を参照し、切り替えや環境準備が必要なら依存作業と確認方法に反映する。

## 変更するパスを特定する

`designs/repository-structure.md` にある構成ツリーと各ディレクトリの役割を基準にし、実際の配置と照合する。構成書が未作成または記入途中なら、案件の指示と実際の配置から分かる範囲で計画する。配置方針と実際の配置が食い違い、今回の作業を左右する場合は、根拠を示して方針を確認する。

フロントエンド、バックエンド、インフラなど、案件の構成に合わせて変更対象をまとめる。作成するディレクトリと、作成・変更・削除するコード、テスト、設定のファイルを、リポジトリのルートからの相対パスで控える。各パスで何を変えるかを作業に対応づける。構成書にない既存の配置を使う場合や、ディレクトリを新設・移動・廃止する場合、役割を変える場合は、構成書に反映するパスと役割を控える。

パスを確定するために調査が必要なら、確認できている範囲と、何を調べれば確定できるかを記録する。調査を先行作業として実行できる場合は、その結果を使う作業と結ぶ。

構成書に追記や修正が必要なら、構成書を更新する作業を設ける。配置や役割を確かめるために必要な実装・検証作業を直接の前提とし、保存した構成ツリーと役割の説明が実装と一致すれば完了とする。

## 完了を確認できる単位に分ける

グラフ上の作業には `T-01`、`T-02` のように `T-` に番号を続けた ID を付ける。着手に必要な前提、作業で得られる結果、関連する受け入れ条件の ID、完了を確かめる方法を記す。一つの作業が複数の条件に、また一つの条件が複数の作業に対応してよい。複数の条件に共通する作業は一つのノードにし、各条件から参照する。実装が不要な条件も、既存テストや手動確認に結び付けて検証対象に残す。

- [単体テストの手順](unit-testing.md#確認する要件を決める) に沿って、単体で確かめる規則、実装前後のテスト、計測範囲を計画する。関連するテストと実装を一つの作業にまとめる場合も、テストを先に行う順序を記す。
- 成果を独立して確かめられ、その成果を他の作業が直接使う場合は、グラフ上の作業として分ける。同じ作業の中で個別に完了を確かめられる工程は、計画書で子作業に分ける。見出し、レイヤー、ファイルの数に合わせて機械的に分ける必要はない。
- 一つの作業の完了確認と、受け入れ条件の検証を区別する。条件の検証に複数の成果が要る場合は、必要な作業 ID を検証方法にすべて示す。独立した結合テストや手動検証の作業が要るならノードにし、必要な作業を前提として結ぶ。

PBI の E2E を計画し、設定した方式で自動テストコードを使う場合は、対象の `specs/<変更名>/e2e/` にテストを用意して実装中に実行する作業を含める。

## 直接の前提を結ぶ

`A → B` は、A の結果がなければ B を完了確認まで進められないことを示す。B 側に A の ID と、必要な結果を書く。複数の結果が必要なら、それぞれを前提にする。

- B が前提にするのは何か、その結果を既存実装で得られるか、A を先に完了しなくても B を確認できるかを順に考える。すでに使える結果は根拠として記し、作業ノードを作らない。
- たとえば、先に更新した契約を消費側で使う、移行結果を新しい読み取り処理で使う、複数の変更を結合して確認する、といった前提は実装や確認の根拠を添えて結ぶ。
- 仕様の記載順、同じファイルを触ること、作業上の好みだけでは辺を張らない。間接的な先行関係は途中の辺からたどれる。途中の作業とは別に成果を直接使う場合だけ、直接の依存としても記録する。
- 外部データや承認が必要な場合は、誰が何を用意し、いつ利用できるかを確かめる。担当者が準備を行い、完了も確認できるなら、その準備を作業ノードにする。満たせるか未確認の前提は記録し、前提を解消してから、それに依存する作業を実行可能と判断する。

作業 ID と依存関係を [実行順を決める手順](order-tasks.md) に渡す。作業内容、依存理由、受け入れ条件との対応は計画に反映するために保持する。
