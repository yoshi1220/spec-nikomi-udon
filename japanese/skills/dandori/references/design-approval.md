# 計画前の設計承認

[同梱 CLI](../../osameru/scripts/osameru.py) の設置先を以下のコマンドで指定する。対象リポジトリで `python3 <osameruスクリプト> settings` を実行し、`design_approval` を読む。設定がない既存案件の既定値は `none`。どの方式でも確認済みの `shikomi.md` が必要で、`shitagaki.md` があれば使う。

利用者が緊急対応などの例外を指定した場合は、指定の役割の人から例外の承認を得た旨と省略理由を利用者から受け取り、対象 PBI の `dandori.md` に両方を記録し、通常の承認照会を省いて計画に進む。プロジェクト設定は他の PBI にも適用されるため、例外は対象 PBI に記録する。再開時は同じ PBI に記録済みの例外を引き継ぐ。

- `none`。事前承認を省き、計画に進む。
- `operational`。利用者が案件の手続きで承認を得てから起動する。起動をもって承認済みとして扱い、承認の再確認や警告を挟まずに進む。
- `pr`。利用可能な PR 連携で対象 PR のレビュー状態を自動取得する。PBI に設計レビュー用 PR の指定があればそれを使い、なければ対象 PBI の作業ブランチから特定する。同じリポジトリの対象設計書案がレビュー対象であることを確認する。承認済みならマージ前でも計画に進む。

GitHub CLI を使う場合は `python3 <osameruスクリプト> --change specs/<変更名> check-design-review` を実行する。PR 番号が指定されている場合は `--pr <番号>` を付ける。自動選択は、対象ブランチの開いている PR が１件で、作業元が同じリポジトリの場合に使う。フォークで作業する場合は PR 番号を指定する。CLI でも他の PR 連携でも、手元の設計書案が PR の先端と有効な承認時点の両方で同じ内容かを照合する。

PR レビュー方式で対象が曖昧、設計書案がない、照会失敗、レビュー待ち、変更要求などで承認済みと確認できなければ、具体的な状況を警告し、続行するか尋ねて回答を待つ。続行なら対象 PBI の `dandori.md` に確認できなかった項目と続行判断をその場で自動記録し、計画作成・再計画時にも保持する。初めて計画を書く場合は先頭を `<!-- dandori-plan: pending -->` とする。停止なら計画に進まない。
