# 結合テスト仕様書の形で E2E テストを計画する

技術構成によってテスト条件が変わる場合は、`designs/technical-context.md` の該当節があれば参照します。対象の環境と使用する基盤は、振る舞いごとの前提に記します。ローカルの代替サービスで確認できる項目と、実基盤が必要な項目を区別し、`ajimi` が実施前に照合できるようにします。

テスト仕様の作成や見直しを始めたら、お品書きがあれば E2E テスト仕様・結果の行を「仕様作成中」にします。既存のリンクと `e2e.md` に記録した結果は引き継ぎます。

1. `shikomi.md` の受け入れ条件と、用意済みの `shitagaki.md` や `e2e.md` を読みます。既存の E2E テスト仕様書を見直す場合は、合意済みの仕様を根拠に手順と期待結果を確認します。今回変える振る舞いと、その影響を受ける振る舞いを選びます。正常時と失敗時を含め、どの条件をどの手順で確認できるかを明示します。テストに必要な環境やデータには、計画中に用意する作業を結び付けます。
2. [E2E テスト仕様書のテンプレート](../assets/e2e.template.md) に沿って、変更用ディレクトリの `e2e.md` を作成します。確認する振る舞いごとに重複しない ID を付け、設計の該当箇所や、対応する受け入れ条件 ID を示します。前提・手順・期待結果を埋め、実施結果は未実施として始めます。画面で確認する結果があり、プロジェクト設定でキャプチャが有効なら、取得場面ごとに、どの画面でどのデータや状態が見えればその ID の期待結果を裏付けられるかを指定します。同じ ID に複数の場面があれば、取得箇所のセルに `- 受付番号の表示<br>- 出荷済みの表示` のように列挙します。表の構造は [CLI の受け渡し形式](../../osameru/references/format.md) を保ちます。
3. 計画の見直しでは既存の `e2e.md` を読み、同じ振る舞いの ID を引き継ぎます。影響を受ける手順・期待結果・実施結果を見直し、再確認が必要な結果を示します。対象範囲の過不足と、各 ID の期待結果を実際に判定できることを確かめたら、[実装計画の検証](write-plan.md#保存前後に照合する) に戻ります。

複数の受け入れ条件とテストが多対多で対応するときは、作業順を検証してから [一時グラフ](work-graph.md) に辺を追加します。必要な作業から受け入れ条件へは `verifies`、受け入れ条件から E2E の振る舞いへは `exercises` を使います。再計画では、[作業グラフを置き換える前に控えた影響先](order-tasks.md#既存の計画を見直す)と、更新後の `affected FILE 起点ID --via requires verifies exercises` の結果を合わせます。旧版でだけ結び付いていたテストも、手順と期待結果を確認してから、合格記録を引き継げるか判断します。

仕様を保存して検証したら、お品書きから `e2e.md` にリンクし、「仕様作成済み」と実施状況を記します。新規なら「未実施」、再確認が必要なら「再確認待ち」とします。仕様に変更がなく有効な実施・確認記録があれば、その状況を引き継ぎます。
