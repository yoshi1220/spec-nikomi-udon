# 依存関係を検証して実行順を決める

## 並べ替えに渡す

作業 ID を一意にする。既存計画では、同じ作業に同じ ID を使う。並び替えだけで振り直さず、新しい作業には既存計画の ID と重複しない番号を使う。

各作業の ID と直接の前提を JSON 配列にし、[order_tasks.py](../scripts/order_tasks.py) に標準入力で渡す。前提がなければ `depends_on` は空配列とする。グラフの入力は作業中だけ保持する。

```sh
python3 /path/to/dandori/scripts/order_tasks.py <<'JSON'
[
  {"id": "T-03", "depends_on": ["T-01", "T-02"]},
  {"id": "T-02", "depends_on": []},
  {"id": "T-01", "depends_on": []}
]
JSON
```

スクリプトは、前提をすべて並べ終えた作業から選んで並べる。候補が複数あれば入力順を優先する。この例の結果は `["T-02", "T-01", "T-03"]`。結果を作業リストの順序に使う。ID の数値順と一致する必要はない。

入力の順序には、利用者が指定した優先順位や、早期に検証できる作業を先にするなどの計画上の判断を反映できる。優先順だけを表す依存は作らない。再計画で優先順位が変わらない場合は、既存の並びを優先する。

## 検証で見つかった問題を解消する

- スクリプトは重複 ID、重複依存、自己依存、存在しない前提、循環を検出すると異常終了する。結果の一部だけを作業リストに採用しない。
- 前提 ID が存在しない場合は、誤記か、作業の抜けか、既存実装ですでに満たされているかを確かめる。完了済みの作業を前提にする場合も、計画に残すなら依存先のノードとして含める。
- 循環があれば、報告された辺を結果の受け渡しに照らして見直す。不要な依存があれば根拠を確かめて外す。共通の契約や準備を先に確定できるなら作業を分ける。相互に依存する変更に独立した完了条件がなく、一緒に検証できるなら一つにまとめる。
- 修正したグラフを再実行する。仕様の判断や未確認の外部前提が残る場合は、影響を受ける作業と解決に必要なことを示し、実行可能な計画として確定しない。

並べ替えに成功したら、[計画を記録して検証する](write-plan.md)。
