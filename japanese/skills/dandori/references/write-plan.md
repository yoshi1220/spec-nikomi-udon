# 計画を記録して検証する

## 作業リストと確認方法を書く

- `shikomi.md` への参照を残す。実装方針には影響範囲と、踏襲する実装方法や再利用する処理を書く。
- 並べ替えの結果を使い、順番に作業を記す。各作業にはチェック欄、作業 ID、完了時に得られる結果、直接の前提の ID と理由、関連する受け入れ条件 ID、完了の確認方法を記す。前提がない場合は「なし」とする。
- 個別に完了を確認できる工程が複数あれば、親作業の直下に実行順でチェック欄を並べる。子作業 ID は `ST-<親作業の番号>-<連番>` とし、連番は親ごとに `01` から始める。たとえば `T-01` の子作業は `ST-01-01`、`ST-01-02` とする。各行に作業内容と確認方法を記す。依存関係と受け入れ条件の対応には親作業 ID を使い、子作業はその親の前提を引き継ぐ。完了条件に違いがない工程を数合わせで増やさない。
- 受け入れ条件ごとに一行設け、確認に必要な作業 ID、テストや手動確認の前提と手順、期待する結果を記す。既存機能だけで検証できる場合は使うテストや手順を示す。新しい条件の結果は「未実施」とする。
- 変更する振る舞いと、その変更で崩れうる既存の振る舞いを、受け入れ条件、仕様本文、既存設計から拾う。振る舞いが崩れたときに観測結果に差が出る前提・入力を選び、確認方法に期待結果と対で記す。たとえば上限値まで受理する仕様なら、上限値での受理と、その直後の値での拒否を確かめる。受け入れ条件に直接対応しない確認は、関連する作業の完了の確認方法に記す。
- グラフの辺は作業リストの「先に済ませる作業」でたどれる。依存関係を持つ別文書は必要ない。

## 既存の計画を更新する

再計画を始めるときは、本文と結果を保ったまま、先頭の状態マーカーを `<!-- dandori-plan: pending -->` に変更して保存する。旧形式でマーカーがなければ先頭に追加する。お品書きがあれば、着手条件を確認する間は実装計画の行を「保留」にする。前提が解消しないまま中断した場合は保留のままにし、実行に進めない理由を伝える。

前の計画と照合する。同じ子作業の ID は書式に合っていれば引き継ぎ、確認結果も有効なら残す。書式の修正で子作業の ID が変わる場合は、計画内の参照と確認結果も新しい ID に対応づける。新しい子作業は未完了から始め、同じ親の中で使ったことのない連番を付ける。以前の計画に親の完了記録しかなければ、子作業の確認方法を満たす根拠がある場合に限り、子作業にも完了を記録する。作業内容、完了条件、確認に使った前提が引き続き有効なら、完了のチェックと検証結果を引き継ぐ。順序だけの変更は完了状態に影響しない。作業内容や前提となる作業の結果が変わった場合は、それに依存する作業をたどり、完了確認や検証結果を引き継げるか判断する。影響を受けた作業のチェックを外し、該当する受け入れ条件は再確認が必要と記録して、理由を添える。古い検証結果を参照用に残す場合も、再確認が必要だと分かるようにする。

## 保存前後に照合する

1. 親作業がスクリプトの出力と同じ順序で、一度ずつ載っている。前提 ID は重複せず、グラフの直接の前提と一致し、すべて先の親作業を指す。子作業は親の直下に実行順で並べる。各 ID が `ST-<親作業の番号>-<連番>` の書式に合っているか、最初の番号がその親作業の番号と一致するか、子作業 ID に重複がないかを確かめる。未完了の子作業があれば親も未完了とする。
2. `shikomi.md` の受け入れ条件がすべて確認表にあり、各条件の確認方法と期待する結果が具体的である。作業の完了確認も含め、対象の振る舞いが崩れたときに差が出る入力と期待結果がある。確認に必要な作業が抜けておらず、作業と確認表で参照する ID が一致している。
3. 単体で確かめる規則とテストが対応し、新規・変更する振る舞いの単体テストコードを実装に先立って追加・更新する計画がある。対象がなければ理由が記録されている。案件の実行・計測方法と範囲も確認する。作業は合意した振る舞い、制約、検証のいずれかを支えている。受け入れ条件に直接対応しない準備作業には、必要とする後続作業または制約を示す。計画が仕様の範囲を超えていないことを確かめる。
4. 案件のフローに E2E テストを含む場合（設計承認が `pr` または `operational` の場合を含む）、または基本設計書案や既存の `e2e.md` がある場合は、[E2E テストを計画し](plan-e2e.md)、`dandori.md` から `e2e.md` へリンクする。状態を `pending` にしたまま `dandori.md` を保存し、読み直して 1〜3 を照合する。すべての確認が済み、実行を妨げる前提も残っていなければ、[approval.py](../../osumitsuki/scripts/approval.py) の `finish-plan` を実行する。再設計と同じロックの中でお品書きの承認状態を読み、先頭のマーカーを実行可能にする。承認待ちなら計画を保留し、承認後に再開する。
5. `oshinagaki.md` があれば、保存した `dandori.md` にリンクする。`finish-plan` が成功したら「作成済み」にする。承認などの前提が残っていれば「保留」、計画を作成・確認している途中なら「作成中」とする。計画の場所と実行に進めるかを伝える。
