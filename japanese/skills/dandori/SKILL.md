# 合意した仕様から実装計画を立てる

利用者が指定したディレクトリを使う。指定がなければ、現在の `feature/<変更名>` ブランチに対応する `specs/<変更名>/` を使う。対象を特定できなければ、ディレクトリを尋ねる。

1. 既存の `dandori.md` があれば読み、[計画を更新する手順](references/write-plan.md#既存の計画を更新する) に従って実行可否を保留にする。`shikomi.md` の先頭行が `<!-- shikomi-review: confirmed -->` で、実装方針や受け入れ条件に関わる未決事項が解消していることを確かめる。仕様の確認が必要なら該当箇所を伝え、利用者の判断を待つ。
   - 対象 PBI の `shitagaki.md` があれば計画に使う。作業を洗い出す前に、[計画前の設計承認](references/design-approval.md) に従ってお品書きの状態を確認する。緊急指定があれば、その理由を記録する。
2. 着手条件がそろったら、お品書きがあれば実装計画の行を「作成中」にし、既存のリンクは残す。[変更対象、作業、依存関係を洗い出す](references/build-task-graph.md)。仕様と既存実装を照合して変更するパスを特定し、個別に完了を確認できる作業に分ける。各作業をノードにし、先に済ませる作業から後続の作業へ辺を引く。各受け入れ条件に、その確認に必要な作業を対応づける。
3. [依存関係を検証して実行順を決める](references/order-tasks.md)。同梱のスクリプトでグラフを検証し、得られた順序を使う。循環や欠けた前提を解消できない場合は、該当作業と必要な判断を伝える。
4. [計画を記録して検証する](references/write-plan.md)。対象ディレクトリの `dandori.md` に実装方針と変更対象をまとめ、そのあとに作業を実行順で並べる。新規の場合は [計画のテンプレート](assets/dandori.template.md) を使う。仕様を変更する必要があれば、該当箇所を示して明確化に戻る。

利用者の判断が必要なときは、一問ずつ確認する。原則として実行可能な 3 案を推奨順に示し、最初の案を勧める理由を添え、自由入力も受け付ける。案を提示できないときは、自由に答えられる質問にする。
