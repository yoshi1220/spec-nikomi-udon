# 合意した仕様から実装計画を立てる

利用者が対象ディレクトリを指定した場合はその指定を使う。指定がなければ、現在の `feature/<変更名>` ブランチに対応する `specs/<変更名>/` を使う。対象を特定できなければ、ディレクトリを尋ねる。

1. `nikomi.md` を読み、利用者の確認を示す `<!-- nikomi-review: confirmed -->` があり、実装方針や受け入れ条件に関わる未決事項が解消していることを確かめる。仕様の確認が必要なら該当箇所を伝え、利用者の判断を待つ。
2. 関連する全体指針、正本、コードとテストを調べる。今回の要件に合う既存の実装方法を踏襲し、利用できる処理を再利用する。別の方法を採る必要があれば、その理由を記録する。
3. 対象ディレクトリの `dandori.md` に計画を書く。新規の場合は [計画のテンプレート](assets/dandori.template.md) を使う。`nikomi.md` への参照を残し、実装方針に影響範囲を書く。作業は、個別に結果を確認できる単位に分けてチェック欄を付け、実行順、依存関係、関連する受け入れ条件 ID と完了確認を書く。条件ごとの欄には、ID、確認方法、結果（初回は未実施）を書く。
4. 全受け入れ条件 ID を照合し、確認方法の漏れや、合意した仕様・制約との矛盾を見直す。既存の `dandori.md` を更新する場合は、影響のない作業のチェックと受け入れ条件の確認結果を保つ。ID が同じでも、影響を受けた作業はチェックを外し、条件は再確認が必要だと記す。

利用者の判断が必要なときは一問ずつ、原則３案を推奨順に提示し、最初の案を推す理由と自由入力を添える。案を提示できないときは、自由に答えられる質問にする。
