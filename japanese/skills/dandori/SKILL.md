# 合意した仕様から実装計画を立てる

利用者が対象ディレクトリを指定した場合はその指定を使う。指定がなければ、現在の `feature/<変更名>` ブランチに対応する `specs/<変更名>/` を使う。対象を特定できなければ、ディレクトリを尋ねる。

1. 既存の `dandori.md` があれば読み、[計画を更新する手順](references/write-plan.md#既存の計画を更新する) に従って実行可否を保留にする。`shikomi.md` を読み、利用者の確認を示す `<!-- shikomi-review: confirmed -->` があり、実装方針や受け入れ条件に関わる未決事項が解消していることを確かめる。仕様の確認が必要なら該当箇所を伝え、利用者の判断を待つ。
   - 対象 PBI の `shitagaki.md` があれば計画に使う。[計画前の設計承認](references/design-approval.md) に従ってお品書きの状態を確認（緊急指定があれば理由を記録）してから作業を洗い出す。
2. [作業と依存関係を洗い出す](references/build-task-graph.md)。仕様と既存実装を照合して作業を分け、作業をノード、先に済ませる必要がある作業から後続作業への辺を依存関係とする。受け入れ条件と確認に必要な作業を対応づける。
3. [依存関係を検証して実行順を決める](references/order-tasks.md)。同梱のスクリプトでグラフを検証し、得られた順序を使う。循環や欠けた前提を解消できない場合は、該当作業と必要な判断を伝える。
4. [計画を記録して検証する](references/write-plan.md)。計画は対象ディレクトリの `dandori.md` にまとめる。新規の場合は [計画のテンプレート](assets/dandori.template.md) を使う。仕様を変更する必要があれば、該当箇所を示して明確化に戻る。

利用者の判断が必要なときは一問ずつ、原則３案を推奨順に提示し、最初の案を推す理由と自由入力を添える。案を提示できないときは、自由に答えられる質問にする。
