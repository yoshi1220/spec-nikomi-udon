# 計画に沿って実装し、結果を残す

利用者が対象ディレクトリを指定した場合はその指定を使う。指定がなければ、現在の `feature/<変更名>` ブランチに対応する `specs/<変更名>/` を使う。対象を特定できない場合や、別の変更のブランチにいる場合は、利用者に作業先を確認する。

1. `nikomi.md` と `dandori.md` を読む。仕様が未確認の場合や実装を妨げる未決事項がある場合は、仕様の明確化に戻る。計画に状態マーカーがある場合は、先頭に `<!-- dandori-plan: ready -->` が一つだけあることを確かめる。保留中や状態が不正な場合は計画に戻る。マーカーがない旧形式でも、計画が現行の確認済み仕様に対応し、すべての受け入れ条件に確認方法があることを確かめてから実装に進む。
2. 作業順に進める。各作業の着手前に、記載された直接の前提がすべて完了し、その確認結果が現在も有効であることを確かめる。前提の参照が不明または順序と矛盾する場合は計画に戻る。前提が未完了または確認に失敗した場合は、該当する後続作業を見送り、理由と前提の作業 ID を記す。前提を満たす別の作業は続けてよい。類似実装を確認し、要件に合う既存の方法とコードを使う。別の方法を採る理由は計画に記す。コード変更では期待する振る舞いを確かめるテストを先に書くことを基本とし、既存テストや所定の確認手順も使う。
3. 各作業の確認が済んだ時点でチェック欄を更新する。受け入れ条件は、確認方法に記載された作業がすべて完了してから検証する。条件ごとに `dandori.md` へ、受け入れ条件 ID、実行したテスト名やコマンドまたは手動確認の内容、実際の結果を記録する。未実施や失敗があればその状態と理由を残す。再開時には過去の結果を読み、その後の変更が影響する確認をやり直す。

   再確認に失敗した作業や、以前の確認結果が無効になった作業はチェックを外す。依存関係を後続へたどり、その結果に直接または間接に依存する作業も未完了に戻す。該当する受け入れ条件は、条件自体の確認に失敗した場合は「失敗」、以前の合格の根拠が無効になった場合は「再確認待ち」とする。影響を受けない記録は保つ。起点の作業 ID と理由を添えて `dandori.md` に保存してから、次の作業へ進む。前提を直した後は、後続作業と受け入れ条件もそれぞれ確認してから完了や合格に戻す。

4. 全作業のチェックと、現在の変更に対してすべての受け入れ条件を満たした検証結果がそろってから完了を報告する。

実装や既存の振る舞いが合意済みの仕様と矛盾し、どちらに合わせるか判断が必要な場合は、観測した結果を記録して該当作業を止める。利用者に一問ずつ尋ね、原則３案を推奨順に提示し、最初の案を推す理由と自由入力を添える。案を提示できないときは、自由に答えられる質問にする。
