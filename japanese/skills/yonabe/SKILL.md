# 計画に沿って実装し、結果を残す

利用者が対象ディレクトリを指定した場合はその指定を使う。指定がなければ、現在の `feature/<変更名>` ブランチに対応する `specs/<変更名>/` を使う。対象を特定できない場合や、別の変更のブランチにいる場合は、利用者に作業先を確認する。

1. `nikomi.md` と `dandori.md` を読む。利用者の確認を示す `<!-- nikomi-review: confirmed -->` があり、計画が現行の仕様に対応していることを確かめる。仕様が未確認の場合や実装を妨げる未決事項がある場合は、仕様の明確化に戻る。計画が古い場合や条件に対応する確認方法が足りない場合は、不足箇所を示して計画に戻る。いずれも解消してから実装に進む。
2. 作業順に実装する。類似実装の作り方を確認し、今回の要件に合う既存の実装方法とコードを使う。別の方法を採る理由があれば計画に記す。テスト駆動開発を基本とし、コードを変える作業ではまず期待する振る舞いを確かめるテストを書く。既存のテストやプロジェクトで定めた確認手順も使う。
3. 各作業の確認が済んだ時点でチェック欄を更新する。条件ごとに `dandori.md` へ、受け入れ条件 ID、実行したテスト名やコマンドまたは手動確認の内容、実際の結果を記録する。未実施や失敗があればその状態と理由を残す。再開時には過去の結果を読み、その後の変更が影響する確認をやり直す。
4. 全作業のチェックと、すべての受け入れ条件を満たした検証結果がそろってから完了を報告する。

実装や既存の振る舞いが合意済みの仕様と矛盾し、どちらに合わせるか判断が必要な場合は、観測した結果を記録して該当作業を止める。利用者に一問ずつ尋ね、原則３案を推奨順に提示し、最初の案を推す理由と自由入力を添える。案を提示できないときは、自由に答えられる質問にする。
