# たたき台を用意する

## 作業ブランチと保存先を用意する

既存の変更の続きであれば、そのブランチと `nikomi.md` を確認して再開する。新しい変更なら入力内容を表す短い名前（例 `export-csv`）を決める。別の変更のブランチを起点にしてよいか分からない場合は、新規作成前に確認する。

1. 設定済みのリモートがあれば `git fetch --all --prune` を実行する。失敗した場合は理由を示し、リモートの最新の連番を確認できていないと伝える。取得済みの情報で続けるか中止するか利用者に尋ね、続行の回答を得てから次へ進む。リモートが未設定なら、ローカルの情報で採番する。
2. 対象リポジトリを作業ディレクトリにして、同梱の [start_change.py](../scripts/start_change.py) を Python 3 で実行する。引数には変更名を一つ渡す。スクリプトはローカルブランチ、取得済みのリモートブランチ、`specs/` 配下の既存ディレクトリを調べ、その最大番号の次を使う。出力されたパスに `nikomi.md` を作る。異常終了したときは、作業ブランチとディレクトリの状態を調べてから再試行を判断する。

## 分かっている情報でたたき台を書く

新規の `nikomi.md` は [仕様のテンプレート](../assets/nikomi.template.md) を使う。先頭の `<!-- nikomi-review: pending -->` を残し、分かっている内容で次の４項目を記入する。

- **目的・対象範囲**。変更する理由と、今回扱う範囲を記す。
- **期待する振る舞い**。利用者の操作や入力と、外から確認できる結果を書く。
- **合意した設計上の判断**。確認済みの判断と理由を残す。プロジェクトの全体指針、既存の正本、類似実装に該当する制約があれば参照する。
- **受け入れ条件**。前提・操作・観測できる結果を書く。条件ごとに重複しない `AC-01` 形式の ID を付け、一度付けた ID は振り直さない。

参照元と、実装方針や受け入れ条件に関わる未決事項を必要に応じて記録する。既存改修では、現在観測できる振る舞いと、維持すると合意した仕様を区別する。

「元の依頼」には、利用者の言葉で求められた機能・制約・対象外を残す。既存資料が主入力なら、資料が示す目標を該当箇所への参照とともに記す。

既存の仕様に「元の依頼」がなければ、参照できる元の入力から目標を確認する。入力が見つからない場合は、記載済みの目的・対象範囲・合意済みの要件を起点にする。既存の見出しと ID を保つ。既存要件の意図が分からなければ、調査する論点として扱う。

## 面談を始める

たたき台を保存したら、必ず [明確化の手順](clarify-spec.md) に進む。再開時には、既存の仕様とそこで確定した判断を読んでから、面談の状態を組み直す。
