# 失敗対応と完了判定

## 原因に応じて次の行動を決める

| 観測したこと | 次に行うこと |
| --- | --- |
| 合意済みの仕様と計画の範囲で直せる実装の不具合 | 失敗したテストや手順から原因を調べ、修正して影響範囲を再確認する。 |
| 検証環境や確認用データが足りない | 実行できなかった確認と、不足している前提を記録する。作業範囲で用意できれば再試行し、利用者の対応が必要なら何を用意してほしいか伝える。 |
| 合意済みの仕様は維持できるが、計画の作業内容、前提、確認方法の見直しが必要 | 根拠と作業 ID を示す。影響を受ける作業を止め、`dandori` に戻る。 |
| 仕様が不明、または現行の振る舞いと食い違い、何を実装するか決められない | 該当仕様と観測結果を「未確認（利用者の確認が必要）」として記録し、影響する作業を止める。利用者に一問ずつ確認し、仕様の明確化が必要なら `shikomi` に戻る。 |

選択肢を示す場合は実行可能な案を原則３つ、推奨順に並べ、最初の案を推す理由と自由入力を添える。案が出せない場合は、自由に答えられる質問にする。保留中も前提を満たす独立した作業は進められる。利用者が中断を求めたら実装を止め、確認済みの結果と再開時に必要な情報を残す。

## 影響を受ける記録を更新する

問題が子作業にあれば、そのチェックを外し、親作業も未完了に戻す。同じ親の内外で確認結果が無効になった子作業を見直し、今も有効な結果は残す。着手時に作った一時グラフで `affected FILE 起点作業ID --via requires verifies` を実行する。子作業からたどる場合は親 ID を使う。起点自身と、返された後続作業・受け入れ条件を計画の記録に照合して次を行う。

1. 再確認に失敗した作業、または以前の確認結果が無効になった作業のチェックを外す。計画の依存関係を後続へたどり、その結果を直接・間接に前提とする作業も未完了に戻す。
2. 該当の受け入れ条件は、条件自体の確認に失敗した場合は「失敗」、以前の合格の根拠が無効になった場合は「再確認待ち」とする。影響が及ばない記録は保つ。
3. 起点の作業 ID と理由を添えて `dandori.md` に保存してから次の作業へ進む。前提の修正後は、後続作業と受け入れ条件をそれぞれ再確認してから完了や合格に戻す。

たとえば、受け入れ条件 `AC-01` が `T-01` と `T-02` を必要とし、`T-02` の前提が `T-01` だとする。再開後に `T-01` の確認が失敗したら、両作業を未完了に戻し、以前合格した `AC-01` は再確認待ちにする。`T-01` を直した後に `T-02` と `AC-01` も再確認する。

## 完了または中断を報告する

- 保存した `dandori.md` と現在の差分を見直す。全作業が完了し、`shikomi.md` の各受け入れ条件に今回の変更に対する有効な合格の根拠があり、プロジェクト所定の検証が通っていることを確かめる。単体テストの実行結果と行カバレッジを [単体テストの手順](../../dandori/references/unit-testing.md#行カバレッジの目標は-80-以上) に従って記録する。必要な単体テストが未実施・不合格なら完了にしない。根拠が足りず、追加で確かめられることがあれば検証を続ける。
- 完了した場合は、作業数、確認した受け入れ条件と結果、`dandori.md` の場所を伝える。残件がある場合は、作業または条件の ID、現状、再開に必要なことを伝える。未実施や再確認待ちの結果を合格として数えない。
