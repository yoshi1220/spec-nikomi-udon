# Step 4. 決定を nikomi.md に記録する

Step 3 の次に実行する工程ではない。ユーザー回答が確定するたびに Step 3 から Step 4A を呼び、調査事実で曖昧さが解消するたびに Step 2 から Step 4B を呼ぶ。調査で受諾済みの決定を変える必要が分かった場合は、決定を保ったまま [面談の規則](interview-rules.md) の矛盾確認に進む。

## Step 4A. ユーザー回答の反映

1. Step 1 で記録した既存の質疑の行数を使う。必要に応じて `## Clarifications` を作り、日付の `### Session YYYY-MM-DD` を使う。同じ日付の見出しがあれば再利用する。
2. 受諾した回答ごとに `- Q: <質問> → A: <確定回答>` を 1 行追記する。後の受諾回答が過去の決定を変える場合は、古い行を残して ` → <後の質問の要旨> により更新: <新しい結果>` を spec の言語で末尾に付ける。本文に存在しなくなった決定を、更新の注記なしに Clarifications へ残さない。
3. 確定した決定を「Step 4C. 共通の反映・検証規則」に従って spec 本体へ反映する。
4. 1 回の回答に複数の決定が含まれる場合は、決定を 1 件ずつ反映・保存・検証する。ただし、同じ要件を変更する決定や相互に依存する決定は 1 回の保存で反映し、回答と矛盾する中間状態を保存しない。Clarifications の Q/A 行は受諾回答につき 1 行のままとし、同じ回答を重複記録しない。
5. 各決定の保存・検証が成功した後、その論点を Resolved へ変更し、カテゴリ集約状態を再計算する。

## Step 4B. 調査で確定した事実の反映

1. nikomi.md の `## Clarifications` / `### Session YYYY-MM-DD` を新設せず、Q/A 行も追記しない。Clarifications はユーザーとの質疑だけを記録する。
2. コードベース・プロジェクト文書・既存 spec から確認できた事実だけを、「Step 4C. 共通の反映・検証規則」に従って spec 本体へ反映する。推測や仮想シナリオは事実として反映しない。
3. 確認した事実を 1 件ずつ反映・保存・検証する。
4. 保存・検証が成功した後、その事実で解消した論点を Resolved へ変更し、カテゴリ集約状態を再計算する。

## 未決事項の記録

今回の変更に関わる未決事項は、文書を読んだ人が次に取るべき行動が分かるように記す。

- **未確認**。根拠が足りない事実や、資料が食い違っていて確認が必要な事実に使う。分かっている範囲と参照元を示す。食い違いがある場合は双方を示し、何を調べるか、どの資料や情報があれば確認できるかを記す。
- **利用者の判断が必要**。仕様・方針を選ぶ必要がある場合に使う。何を決めるか、理由、影響する仕様・作業・検証を記す。事実を利用者に提供してもらう場合も、その事実は「未確認」のまま扱う。

実装方針や受け入れ検証を妨げる点には、その影響も明記する。対話中は「未決事項」に置く。既存の仕様に該当する欄がなければ、必要に応じて「未決事項」の見出しを追加する。対話終了時には、実装や受け入れ検証を妨げる点と、Step 4C が記録を求める保留を、「未決」の表示と上の区分を添えて「対象外と制限事項」に移す。既に同じ項目があれば更新し、二重に記録しない。解消した項目は、根拠とともに仕様へ反映してから未決の記録を取り除く。

## Step 4C. 共通の反映・検証規則

1. 内容を最も適したセクションへ反映する。
   - 機能の曖昧さは「機能要件」
   - 担当者や操作の区別は「アクターと権限」
   - データの構成は「データと状態」（順序を保ち、制約は簡潔に）
   - 非機能要件は「非機能要件」に、合意した検証可能な条件を記す。指標を使う場合は、合意した値や測り方を記す
   - 例外は「エッジケースと失敗処理」
   - 用語 → spec 全体で正準用語に正規化（必要なら `（旧称 "X"）` を一度だけ）
   - 適切なセクションが無ければ、概要の散文へ追記せず、既存の最上位セクションと同じ階層に**標準の見出しを追加する**。プロジェクトのテンプレートに名前があればそれを使い、無ければ spec の言語で「アクターと権限」「機能要件」「データと状態」「エッジケースと失敗処理」「非機能要件」「受け入れ条件」「対象外と制限事項」「確認済みの前提」を使う。「確認済みの前提」には Step 4B で反映した各事実と出典を記録する。元の依頼文は起点として残し、範囲の修正は合意した決定に記録し、既存セクションの改名・並べ替え・統合もしない。
   - すべての要件を、独立してテスト可能な番号付きの箇条書きとして書き、散文段落へ書き足さない。セクションごとの ID 接頭辞は、AP-（アクターと権限）、FR-（機能要件）、DS-（データと状態）、EC-（エッジケースと失敗処理）、NFR-（非機能要件）、AC-（受け入れ条件）、OS-（対象外と制限事項）、VP-（確認済みの前提）とする。新規項目はセクション末尾へ次の番号で加え、上から読んで番号順になるようにする。既存 ID は振り直さず、削除による欠番は許容する。プロジェクトのテンプレートが独自 ID を定めていれば従う。通常 1〜2 文で規則だけを書き、背景・理由・質問を繰り返さない。帰結で確定した要件は根拠となる保存済み質問の要旨や、確認済みの前提の ID を引用する。状態変化は、契機となるイベント、変わる数量・状態、各当事者に見える結果を明示する。合意済みの除外・制限・拡張は理由とともに「対象外と制限事項」へ記録し、除外・制限には満たせなくなる目標または事実も示す。気づいたが質問しなかった状況はすべて記録する。Outstanding / Deferred の論点のうち、目標の挙動を未定義のまま残すものも記録する。いずれも、合意済みの除外と誤読されないよう「未決」と明記し、1 件 1 行で記録する。論点・状態・理由と、ユーザー決定か不足する事実のどちらがあれば解消するかを示す（例: 「未決（未質問）: <状況>：<理由>。ユーザーの決定が必要」）。spec だけで未解消事項が分かるようにし、解消後はその行を削除する。
2. 新しい内容が過去の曖昧な記述を無効化するなら、重複追記ではなく**置換**する。矛盾する古い記述を残さない。後の決定が既存要件に例外・条件・別のケースを加える場合は、その ID の要件を直接修正し、別の場所から上書きする要件を加えない。新しい規則にだけ新規 ID を付ける。
3. **目標の挙動・境界・失敗結果を定める各決定から、受け入れ条件を導く。** 「受け入れ条件」へ`### AC-04` のような見出しと短いシナリオを加え、前提、操作、観測可能な結果を、区別に必要な最小限の数量で述べる。検証する決定を引用する。数字だけが異なるシナリオは統合する。除外・対象外のシナリオは作らず「対象外と制限事項」に記録する。「拒否しなければならない」操作は除外でなく制約なので、拒否を確認するシナリオを作る。受諾済みの値だけを使う。数量は「例」と明記し、特定の数字に結果が依存しない場合に限り例示してよい。確認項目から新しい要件を生まない。未受諾の閾値・目標・能力が必要ならシナリオは書かず、その値の質問候補を作り、「数値目標を設けない」も選択肢に入れる。
4. **反映のたびに nikomi.md を保存する。** 全体を書き直さず、該当行だけを挿入・置換し、保存済み差分が意図した行だけを変えていることを確認する。無関係なセクションの並び・見出し階層は変えない。追記は最小限かつテスト可能な形に保つ。
5. **保存のたびに検証する**（最終ラウンド後にも仕様全体を 1 回検証する）。
   - Step 4A では保存したファイルを読み直して Clarifications の行数を数える。受諾済み回答につき重複のない 1 行が必要で、開始前から増えた行が今回の受諾数と異なる場合は、次の質問前に修正する。Step 4B では Clarifications に差分が無いことを確認する
   - 要件・シナリオ ID が spec 内で一意かつセクション内で昇順で、別セクションの要件による上書きがない。更新された旧決定の要件とシナリオも同じ処理で修正されている
   - イベントの順序で結果が変わる場合は、仕様に順序付けの規則があり、受け入れシナリオでその結果を確かめられる。記録によって規則が異なる場合は、その組み合わせも確かめる
   - 反映内容が解消するはずだった曖昧な記述・プレースホルダが残っていない
   - 残った未決事項について、確認すべき事実または利用者が決めることとその影響が明記され、仕様や受け入れ条件で確定扱いされていない
   - 無効化された選択肢・矛盾する古い記述が残っていない
   - Markdown 構造が正しい。既存の見出しを保つ。必要な標準セクション、Step 4A の質疑、受け入れ条件の見出しだけを追加する
   - 新規要件はすべて番号付きで、各受け入れシナリオが対応する要件、受諾済みの決定、確認済みの規則のいずれかを参照し、未受諾の値を使っていない。Clarifications に更新注記のないまま本文と矛盾する行がない
   - 更新した全セクションで正準用語が一貫している

新たな回答がない帰結は、要件に受諾済みの規則と確認済みの事実を引用し、質疑を追加しない。以前のセッションの決定を引用するときは、保存済みの記録と質問の要旨を使う。
