# 設定・記録・正本への反映

導入先のリポジトリで、同梱の [osameru.py](../scripts/osameru.py) を Python 3.8 以降で実行します。以下の `<osameru.py>` は導入先に配置したスクリプトのパスです。変更用ディレクトリは、現在の `feature/<変更名>` ブランチから選びます。ディレクトリを明示するときは、サブコマンドの前に `--change specs/<変更名>` を付けます。`apply` は対応する作業ブランチで行います。

## プロジェクトの設定

初回の `init` で案件の初期値を選びます。導入後は、リポジトリ内で `python3 <osameru.py> setup --method agent-browser` のように指定すると、選んだ項目だけを変更できます。`--method` の値は `playwright`、`chrome-extension`、`manual`、`agent-browser` です。画面項目定義書と画面キャプチャは既定で無効です。必要に応じて `--screen-items on`、`--screenshots on` を指定します。`settings` は `designs/nikomi-udon.json` の有効な設定を表示します。設定ファイルがない案件では手動テストを使います。

現在の設定でテストを実施し、結果の確認を記録します。設定を変更した後の反映には、新しい設定での実施と確認が必要です。

計画前の設計承認は、導入時または設定変更時に `setup` の `--design-approval` で選べます。指定できる値は `none`（既定）、`operational`、`pr` です。

## 設計書案のブロック

設計案と一緒に[構造変更案](structure.md)を用意し、設計承認・E2E の前に照合値を `shitagaki.md` に記録します。反映先の文書ごとに完成した本文を一つ置きます。一文書に複数機能がある場合は、それぞれの固定IDが付いた節を含めます。

案件書式の先頭が `# ` の見出しなら、機能別の本文もその見出しで始めます。表や文書属性から始まる書式では、その形式の本文をブロック内に置きます。

基本設計案を作成・更新するときは各ブロックに `requires_heading` を記録します。本文書式を読み、先頭の空白を除いて `# ` で始まれば `true`、それ以外は `false` です。空の書式は担当者に確認します。正本反映時は案に記録した条件を使います。画面項目定義のブロックは `path` と `base` を記録します。

```markdown
<!-- osameru-target: {"path":"orders/register.md","base":"new","requires_heading":true} -->
# 受注登録 基本設計書
<!-- spec-node: order-entry -->

本文
<!-- /osameru-target -->
```

`path` は `designs/specifications/` からの相対パスです。`python3 <osameru.py> base orders/register.md` で、執筆の基にした正本の値を取得します。新規の場合は `new`、既存文書の場合はファイルの SHA-256 を記録します。正本が更新済みの場合は、最新の内容と案を照合してから `base` を取り直します。

画面項目定義書が有効な場合は、`shitagaki.md` のブロック外に `<!-- screen-items: applicable -->` または `<!-- screen-items: not-applicable -->` を一つ記します。対象がある場合は `screen-items.md` に同形式のブロックを置き、反映先には `orders/register.screen-items.md` のようなパスを使います。

## E2E テストの記録と反映

1. テストを開始する直前に `python3 <osameru.py> start-e2e` を実行し、表示された実行 ID を控えます。CLI はテストの定義、プロジェクト設定、作業ツリーの関連ファイルから照合用のハッシュを計算し、前回の結果欄と確認欄をリセットします。報告書から参照するログや画像は PBI 内の `evidence/<実行ID>/` に置きます。Playwright の新規実行には、対象 PBI の `e2e/` にテストファイルが必要です。対象 PBI の `e2e/` にあるテストコードと入力データは、Git の無視対象でも照合します。リンクを使う場合は、作業ツリー内の参照先も照合します。新規実行では、作業ツリー内の未追跡の Python・pytest キャッシュを照合から除きます。Git で追跡するファイルと、テストから明示的にリンクした入力は照合します。ランナーのログやレポートなどの一時出力は、テストディレクトリの外の Git の無視対象の場所に保存します。
2. 実施した方法・環境・日付は `e2e:execution` の区切り内に記録します。新しい実行を始めるとこの欄は初期化され、旧書式には欄が追加されます。予定した対象範囲や共通の事前条件が変わった場合は新しい実行が必要です。`e2e.md` の各振る舞い ID に、今回観測した結果と合否を記録します。証跡欄にはログや画像への Markdown のインラインリンクを記します。CLI は `e2e.md` からの相対パスでファイルを読み、担当者の確認時の内容と照合します。画面キャプチャが有効で取得箇所を指定した行には、`./evidence/<実行ID>/E2E-01.png` などの画像へのリンクを記します。複数の場面を `- 受付<br>- 出荷済み` と指定したら、証跡欄のリンク名も `受付` と `出荷済み` にそろえます。`review-e2e` は各場面に今回の空でない別々の画像が対応することを確認します。担当者は画像を開いて表示内容を確認します。
3. 必須項目がすべて `OK` となり、担当者が今回の実施内容と結果を確認したら、`python3 <osameru.py> review-e2e --tested <実行ID> --reviewer "<確認者名>"` で、同じ `e2e.md` に確認を記録します。入力を変更した場合は、新しい実行を開始して結果と確認を取り直します。`verify-e2e` は記録を検証します。
4. レビューした設計案と、それに結び付けた構造変更案を `python3 <osameru.py> apply` で反映します。`structure-check` と差分で現行 GraphML、本文索引、ノードごとの改訂履歴を確認します。未移行の案件で固定IDと構造変更案のない旧設計案を完了するときは、初回の `apply` に `--reason "<変更理由>"` を渡して従来の文書別履歴に反映します。

確認を取り下げるときは、`e2e:review` の開始・終了コメントの間を「未確認」に戻します。再確認する場合は、`start-e2e` で新しい実行を始めます。旧形式の文書別履歴で変更理由を訂正する場合は、`apply` に訂正後の理由を渡すと同じ PBI の履歴が更新されます。

実施済みの結果の記入や確認を再開する場合は、`e2e.md` の `e2e-run` コメントにある `id` を引き継ぎます。`python3 <osameru.py> check-e2e-run --tested <実行ID>` は、実行 ID とテスト時の入力を照合します。結果や確認の記録は更新しません。

テスト仕様書の `e2e:checks`、`e2e:execution`、`e2e:review` はそれぞれ独立した区切りで囲みます。テスト表は振る舞い ID、確認内容、前提・データ、手順、期待結果、キャプチャ取得箇所、実施結果、判定、証跡の順です。セルの改行は `<br>`、セル内の縦棒は `\|` で記します。判定が確定した項目は `OK` または `NG` と記します。
