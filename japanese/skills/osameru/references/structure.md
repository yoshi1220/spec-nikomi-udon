# 正本の構造と改訂履歴

案件の作業ツリーで同梱の [osameru.py](../scripts/osameru.py) を使う。永続 GraphML の照会には[グラフ操作](../../dandori/references/work-graph.md)の `show`、`order`、`affected` を利用できる。作業用の一時グラフの後片付けは、一時領域で作ったファイルに対して行う。

| `designs/specifications/` 配下 | 内容 |
| --- | --- |
| `structure/current.graphml` | 現行機能・分類、親子関係、機能の有向依存、仕様本文の明示参照 |
| `structure/index.json`、`structure/hierarchy.md` | 固定IDに対応する本文の実パス・見出し・節の照合値と、グラフから生成した階層表示 |
| `structure/notes/<ID>.md` | 任意の説明。階層表示には固定IDで引き継ぐ。旧配置を前提にした記述は再編時に見直す |
| `history/changes.graphml` | 一件の変更から前後のノード、当時の本文の所在、関係と上位の階層をたどる履歴 |
| `history/nodes/<ID>.json` | 元のノードと改訂、引き継いだ内容、出典を含むノード別履歴 |
| `history/retired/<ID>/<commit>.md` | 廃止直前のコミットから取り出した節の本文。変更前ノードに保存先・コミット・当時のパス・固定IDを残す |

## ノードの識別とレビュー

独立して変更・レビューできる機能や仕様に固定IDを付ける。「システム → 受注 → 受注入力」のように案件の集約単位に沿って階層を作る。対象の節の Markdown 見出し直後に固定IDのマーカーを置く。見出しのない文書は先頭行に置く。見出しがなく YAML フロントマターがある場合は、閉じ区切りの直後にマーカーを置く。フロントマターの次が固定ID付きの見出しなら、そのメタデータは先頭の節の改訂に含める。同一文書に複数ノードを含めてよい。マーカーのない小見出しは上位の節に属する。別ファイルへの分割は読みやすさと個別に改訂する頻度で判断する。

移動・改名は同じIDを引き継ぐ。上位の分類を改名・移動した場合は、階層上の経路が変わる子孫の履歴からも変更前後をたどれる。分割では元の範囲を継ぐ親または分割先にIDを残し、それで範囲がずれるときは各分割先に新IDを付けて旧IDとの対応を履歴に残す。吸収なら受け入れる側のID、新しい機能に統合するなら新IDを使う。各改訂の適用範囲に応じて引き継ぎ先を決める。共通改訂は該当する各履歴に出典付きで複写し、再統合時は同じ改訂を一件にまとめる。対象の子が不明な旧改訂は、確認できた親に原文・出典・未確認の範囲を残す。本文のあるノードを現行から外すときは、後継が新IDの場合も廃止直前の本文を保存する。

通常改訂はトップ直下の分類と照合し、新分類・新機能をトップ直下に設ける案も検討する。呼び出し・データ連携・本文参照をたどって影響範囲を調べる。全体への関係は共通の親に、個別の関係は対象の子に結ぶ。判断がつかなければ調査を広げ、全件点検も検討する。依存先を確定してから反映し、資料で決まらない場合は候補と根拠を示して利用者に尋ねる。既存階層の組み替え・仕様ファイルの分割は利用者の承認を得る。全体を作り直す場合は全件の配置と関係を点検し、機能別レビューを経て一括で取り込む。レビュー中に現行版が改訂されたら取り込んで影響範囲を再レビューする。範囲が不明か、分類全体の前提が変わった場合は全件点検に戻る。

## 変更の準備と反映

PBI では `shitagaki.md` の隣に `structure-plan.json` を置き、設計承認・E2E の前に両方を用意する。関係だけの変更や文書全体の廃止は、設計案に内容と計画の照合値を記す。反映ブロックは更新後の本文がある文書に付ける。更新する本文は従来どおり正本反映ブロックに全文を記す。案件の書式と既存の固定IDを引き継ぐ。設計案に構造変更案の照合値を記録し、設計 PR には両方を含めてレビューする。既存案件の導入・文書だけの再編は作業ツリーに計画を用意し、`documents` に文書案を入れる。作成差分をレビューし、共有ブランチへのマージで正本を更新する。

二つのノードを初めて作る場合の例（既存案件の導入では `revision` に調査コミットを加える）。

```json
{
  "event": "orders-baseline",
  "reason": "調査版で確認した受注入力を初回記録",
  "base": "new",
  "graph": {
    "nodes": {
      "orders": {"label": "受注", "status": "group"},
      "order-entry": {"label": "受注入力"}
    },
    "edges": {
      "orders-entry": {"source": "orders", "target": "order-entry", "kind": "contains"}
    }
  },
  "documents": {
    "orders/entry.md": {"base": "new", "text": "# 受注入力\n<!-- spec-node: order-entry -->\n\n担当者が注文を入力する。\n"}
  }
}
```

- `event` は一件の変更を識別する。同じイベントIDを再利用できるのは、元の PBI または文書専用の手順で同じ変更を再実行するときに限る。イベント・ノードのIDは英数字で始まる96文字以内の英数字・ハイフン・アンダースコアとする。パスの移植性のため小文字を推奨する。
- PBI では `python3 <osameru.py> structure-plan-digest specs/<変更名>/structure-plan.json` が出力するマーカーを `shitagaki.md` の反映ブロック外に記す。`structure-preview` で設計案と構造変更案を合わせてプレビューする。照合値は改行を LF にそろえて計算するため、Git のチェックアウト時に改行コードが変わっても同じマーカーを使える。計画を変更したら照合値を更新し、設計案を再レビューする。
- 案を作る前に `python3 <osameru.py> structure-base` で構造の `base`、`base orders/entry.md` で文書の `base` を控える。本文だけの改訂では `graph` を省略できる。導入時には調査したコミットの完全なIDを `revision` に記す。初回記録はその版で既存の機能を確認したことを示す。既存の改訂履歴は移行し、コードだけの案件は調査版を履歴の起点とする。
- `graph` は差分。ノードに `label` と必要に応じて `status` を記す。既定は `documented`、分類は `group`、存在を確認し本文が未整備の機能は `undocumented`。辺には `source`、`target`、`kind` を記す。種類は `contains`（親→子）、`calls`（呼び出し元→先）、`transfers`（送信→受信）、`depends`（利用側→前提）、`references`（参照元本文→参照先）。`evidence` に根拠となるパスと見出しやシンボルを記す。辺を付け替えるには同じ辺のIDを指定する。削除は `drop_edges`、`drop_nodes` にIDを列挙し、関係の変更を同じイベントに含める。包含は各ノードの親が最大一つの木の集合にする。
- 任意の `documents` は文書パスに `base` と UTF-8 の本文全体を対応させる。削除は `text: null`。PBI の設計案ブロックを使うパスは一度だけ指定する。本文を直接移動・改名した場合は任意の `refresh` 配列に確認した旧パスと新パスを列挙する。CLI は固定IDから現在位置を読み取る。大文字小文字を区別しない環境で名前の大小文字だけを変える場合は、文書ブランチで実際に改名し、旧名と新名を `refresh` に記す。同じ場所の `文書名.screen-items.md` は設計書のノードに対応し、項目定義の改訂も履歴に残る。文書だけの改訂でも、索引にある設計の画面項目定義を追加・変更・削除する場合は、そのパスを `documents` に含める。直接編集した場合は、差分を確認したパスを `refresh` に記す。PBI で新規に索引へ載せる項目定義や変更した項目定義は、レビューする画面項目の反映ブロックに含める。名前や場所が異なる場合は、大文字・小文字も含めて実際の相対パスをノードの `screen` 属性に記す。索引に登録済みで内容が変わらない項目定義へ付け替える場合は、グラフの変更だけで反映できる。作業差分全体を点検して対象の編集を確認する。現行の索引の対象から `history/`・`structure/` および旧 `*.history.md` を除く。廃止時の `revision` は索引にある直前の本文を含むコミット。省略時は HEAD。
- PBI でノードの説明を改訂するときは、計画の `notes` に固定IDと説明の全文を記す。削除は `null` とし、設計案と一緒にレビューする。
- 履歴の継承は `inherit` に `{"from":"order-entry","to":"domestic-entry","entries":["order-entry/orders-baseline"]}` のように記す。元履歴の `origin/event` を列挙し、すべて該当する場合は `"*"` も使える。共通改訂は国内・海外の分割先にそれぞれ指定する。統合では複数の元ノードから同じ統合先を指定する。引き継ぎ先の履歴から元の内容と出典を読める。
- 旧文書別履歴の移行は `legacy` に元の `path`、SHA-256 の `base`、移行先 `to`、必要に応じて原文の抜粋 `text` と適用範囲の説明 `scope` を記す。抜粋を省けば全文を引き継ぐ。対象があいまいな改訂は確認できた親を指定する。元の各改訂を新しいノードからたどれることを照合する。
- 導入・文書専用の改訂は `python3 <osameru.py> structure PLAN --preview` で対象を確認し、`structure PLAN` で反映する。PBI は通常の E2E 確認を経て、計画に記載した理由で `apply --reason` を実行する。どちらも作業ツリーの本文・グラフ・履歴を更新する。`structure-check` と差分で、継承した改訂と分割前後の関係を確認する。履歴グラフの `change/<event>` とその隣接ノードから一件の経緯をたどれる。
- 中断時は作業差分を確認し、書き込みが途中なら `structure-resume` で反映前後を照合して未反映分を進める。どちらの状態とも一致しない手修正があれば、元の作業ツリーを保存し、更新前の版から別の作業ツリーで再適用して差分から取り込む。中断によるロックが残った場合は、記録されたプロセスが終了したことを確認してからロックを退避する。同じ反映を再実行しても履歴は重複しない。

旧固定IDから調べるときは、正本ディレクトリで照会用ヘルパーの `show history/changes.graphml ID` を実行する。`occurrence` の辺から変更前後の記録を開き、その記録を `show` すると該当する変更と当時の依存関係をたどれる。
