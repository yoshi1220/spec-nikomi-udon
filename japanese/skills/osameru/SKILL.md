# 仕様を正本に納める

`nikomu` で実装し、`ajimi` で E2E テストの合格と担当者の確認を記録した変更を対象とします。[受け渡し形式と CLI](references/format.md) に従い、作業ブランチに正本と改訂履歴の更新を用意します。

通常の改訂、導入、再編、作業の再開には、[正本の構造と履歴](references/structure.md)を参照します。文書だけを再編する場合は、文書ブランチでプレビューし、反映後に検証します。PBI の設計案は、E2E の確認後に次の手順で反映します。

1. 利用者が指定した `specs/<変更名>/` を使います。指定がなければ現在の `feature/<変更名>` から対象を選びます。作業ブランチと対象の変更が対応すること、`shikomi.md` と `shitagaki.md` が存在することを確認します。
2. `shikomi.md`、`shitagaki.md`、`e2e.md` を照合します。設計案の必須項目、未確認事項、E2E の範囲を確認します。要件と実装・設計が食い違う場合や、設計の根拠が足りない場合は、該当箇所を示して利用者に一問ずつ確認します。構造変更案がある場合は `structure-preview` で本文と一緒に照合します。
3. CLI の `apply` を実行します。構造変更案があれば、そこに記録した変更理由が使われます。構造変更案のない旧形式の設計案を初めて反映するときは、変更理由を `--reason` で渡します。CLI が、現在の変更に対する必須 E2E テストの合格と担当者の確認済み記録を照合します。反映できなければ理由を伝え、設計の手直しや再確認が必要な工程へ戻ります。
4. 設計書と改訂履歴の差分を読み直します。構造管理の対象は `structure-check` で検証します。変更用ディレクトリの `oshinagaki.md` に、反映先と作業ブランチへの反映状況を記録します。実装と設計書の更新を同じ PR でレビューできることを報告します。設計書のレビュー後、その PR をマージすると正本の更新が完了します。PR の送信やマージは利用者の依頼を受けて行います。
