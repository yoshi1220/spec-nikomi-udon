# 要件定義資料から構造を読み取る

機能ツリーと関係グラフは、それぞれ資料で根拠を確認できる範囲まで作る。根拠を見返せるよう、資料の章、ページ、表の行、図、利用者の説明などを控える。資料に記載された制約や利用者は、ツリーやグラフに表せない場合も全体指針の該当箇所に残す。

資料から枝や辺を抽出できたら、[一時 GraphML の操作](../../dandori/references/work-graph.md)で機能・システムをノードにし、辺には種類と根拠を付ける。包含は親から子へ `contains` を張り、`order FILE contains` で循環を確認する。連携は資料どおりの向きと種類を保持し、`show FILE ID` で各機能の親・連携先と根拠を照合して全体指針に反映する。

## 根拠に応じて作成する範囲

| 入力にある情報 | 全体指針に書く内容 |
| --- | --- |
| 目的、利用者、対象範囲 | 確認できる概要を書く。機能や連携の情報が足りなければ「未確認」と記す。 |
| 機能名や機能ごとの説明 | 機能一覧を作る。分かる範囲で、その機能でできることを書く。 |
| 機能の分類や親子関係を示す機能一覧、メニュー、本文など | 根拠のある枝と深さまで機能ツリーを作る。親が分からない機能は一覧に残す。 |
| 機能・システム間の関係で、両端、種類、方向が分かる箇所 | 根拠のある辺を有向グラフとして記録する。 |
| 関係はあるが、相手・種類・方向のいずれかが不明な箇所 | 分かる事実を本文に残し、不明な点を「未確認」とする。その関係の辺は作らない。 |

## 機能ツリーを作る

- 資料が示す機能の親子関係を、入れ子の箇条書きで表す。枝の根拠を該当する項目や枝のまとまりに添える。資料の章立ては、それ自体が機能の分類を示していると確認できる場合に使う。
- 同じ機能が複数の分類に属すると明記されていれば、共通機能として一度説明し、各分類から参照する。主たる所属が分からないときは推測で親を選ばない。
- 親子関係が循環する場合は、同名の別機能を混同していないか、包含と依存を取り違えていないかを確かめる。食い違いが残る枝は未確認とする。機能ツリーからプログラムの配置を推定しない。

## 基本設計書の配置方針をまとめる

- メニュー一覧、機能一覧、業務資料などに機能の分類があれば、[配置方針のテンプレート](../assets/basic-design-hierarchy.template.md) を使い、`designs/basic-design-hierarchy.md` に設計書の階層をまとめる。業務上のまとまりを分類にし、独立して設計・改訂できる機能をその下に置く。画面へのショートカットや別メニューに現れる同じ機能は参照で示し、本文の配置先は一つにする。API やバッチなど、メニューに出ない機能も資料で所属が分かれば含める。
- 保存済みの配置方針や正本があれば先に読み、同じ機能の ID と保存先を引き継ぐ。分類と機能には重複しない固定 ID を付ける。新しい ID は `order-entry` のように小文字の英数字とハイフンで付ける。分類のディレクトリと機能の予定ファイルは `designs/specifications/` からの相対パスで示し、各枝に資料名と該当箇所を添える。既存の正本の移動や再編が必要なら、候補と理由を未確認の欄に記す。
- 所属が決まらない機能や資料間で食い違う枝は未確認の欄に残す。分類の根拠がなければ、初回反映のための階層を推測で作らない。既存の方針は残し、保存した方針へのリンクを全体指針に載せる。

## 関係グラフを作る

- ノードには、資料で確認できる機能やシステムを使う。表では起点から終点へ向かう一行を一つの辺とし、関係の種類と根拠を記す。呼び出しは呼び出し元から呼び出し先、データ送信は送信元から受信先、依存は依存する側から依存される側へ向ける。受け渡すデータや適用条件が分かれば添える。
- 同名の機能やシステムが実際には別の要素なら、所属などで区別する。同じ要素だと確認できない場合は、統合せず未確認の点を残す。
- 双方向の連携は、両方向が成立する根拠があるときにそれぞれの辺を記す。資料によって同じ連携の方向が逆になっている場合は、適用条件や版の違いを確かめる。食い違いが残れば未確認とする。異なる種類の関係が同じ二つの要素を結ぶ場合や、根拠のある循環はそのまま残す。グラフは作業の実行順を表すものではない。

## 確認して保存する

- 資料間または既存文書との食い違いは、該当する記述と双方の参照元を記し、未確認とする。対立する情報から確定した枝や辺を追加しない。既存の記述は判断が済むまで保ち、その箇所から未確認の記録をたどれるようにする。利用者に確認するときは、影響する点から一問ずつ尋ねる。回答を待つ間も、根拠のある部分はまとめられる。
- 保存前に、枝や辺ごとに根拠をたどれるか確かめる。各辺の両端、種類、方向が分かり、未確認の点を本文で見分けられることも確認する。
- 手元の資料を調べても残る不明点は「未確認」と記し、「利用者の確認が必要な点」にまとめる。必要な資料、確かめてほしい事実、決めてほしい方針など、確認の内容と理由、影響する箇所を記す。親が分からない機能は一覧に残し、親が未確認であることを示す。根拠がそろうまで分類や関係は確定扱いにしない。
- 既存文書を更新する場合は、古い「確認・判断が必要な点」があれば、その欄を使って現在の見出しと表記にそろえる。保存後、利用者に確認してほしいことを伝える。残件が複数あれば記録を案内し、最も影響のある点から一問ずつ確認する。

## 入力が部分的な例

機能一覧に「受注入力」と「受注照会」が載り、分類は書かれていないとする。連携表に「受注入力が在庫システムを呼び出す」とあり、別の項目には「会計システムと連携する」とだけある。この場合、機能は一覧で示す。グラフには「受注入力 → 在庫システム」の呼び出しを、連携表の位置とともに記す。会計連携は、確認できた事実を記し、種類・方向など、資料で特定できない点を本文に残す。
