# 技術構成を作成・更新する

## ひな形と入力を用意する

[技術構成のひな形](../assets/technical-context.template.md)を使い、`designs/technical-context.md` に7つの節をひな形の順序で用意する。記入済みの内容と有効な判断を引き継ぐ。別のディレクトリにある下書きを取り込むときは、相対リンクを `designs/` から同じ資料・節を開けるパスに直す。

- 空のひな形、担当者の下書き、指定された要件資料のいずれからでも対話を始められる。資料に記載された事実や採用決定を根拠とともに記入し、候補や提案は未決として扱う。
- 既存案件では、調査対象のコミットのコード、依存関係定義、Compose や配置設定、既存設計から分かる情報を先に記入する。対象環境と、調査した版や設定キーなど根拠を特定できる参照先を添える。たとえば Compose の DB 定義はローカル設定の根拠になる。本番の稼働構成には本番についての根拠を使う。

全体指針 `designs/system-overview.md` には、同じディレクトリの `technical-context.md` への相対リンクを置く。既存のリンクは再利用する。新設する場合は表題の直後に置き、確認済みの機能一覧・関係の節を保つ。全体指針が未作成なら、リンクを含む[全体指針のひな形](../assets/system-overview.template.md)を使い、確認できた範囲で作成する。最初の質問の前に両文書を保存する。

## 一問ずつ確認する

全体を見直す場合はひな形の見出し順に進む。節を指定された場合はその節を確認し、関連する節への影響を伝える。不明な事実、資料間の食い違い、未決の選択を一問ずつ扱う。たとえばローカルの DB だけが判明していれば、本番で何が稼働しているかを尋ね、回答の根拠を記す。UI ライブラリの選定などで候補がある場合は、選択肢を推奨順に示す。最初の案を勧める理由を添え、自由入力も受け付ける。根拠が食い違う場合は双方を示し、解消するまで未確認として扱う。

回答ごとに合意と根拠を保存する。確かめられない事実は「未確認」、まだ選んでいない技術は「未決」、使わないと確認できた領域は「該当なし」と記す。未確認事項には必要な情報と影響を添える。再開時は保存済みの節を読み、判断に影響する資料の変更を確認し、残っている項目から進める。

## 環境別の構成を維持する

各節に採用技術と役割を記し、環境差、設計書や設定の参照先を添える。秘密値の代わりに、必要に応じて設定キーや管理手順を参照する。

採用を決めた時点で、対象の環境、移行先の構成、決定の根拠を記録する。運用記録や担当者の確認などで適用を確かめたら、その環境の現行構成を更新する。まだ適用していない環境については、移行予定を残す。たとえば検証環境だけが新しい認証基盤に切り替わった場合、本番の現行構成には旧基盤を、移行先には新基盤を記す。

保存後は、全体指針のリンクから技術構成を開けることと、各節から根拠をたどれることを確かめる。環境ごとに現行構成と移行先を見分けられるかも確認する。作成・更新した節と、後の判断に影響する未確認事項を伝える。
