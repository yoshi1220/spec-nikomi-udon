# 要件定義資料から構造を読み取る

機能ツリーと関係グラフは別々に判断する。どちらも、資料で確認できる部分から作る。章、ページ、表の行、図、または利用者の説明など、判断の根拠に戻れる位置を控える。資料にある制約や利用者は、ツリーやグラフに表せない場合も全体指針の該当箇所に残す。

## 根拠に応じて作成する範囲

| 入力にある情報 | 全体指針に書く内容 |
| --- | --- |
| 目的、利用者、対象範囲 | 確認できる概要を書く。機能や連携の情報が足りなければ「未確認」と記す。 |
| 機能名や機能ごとの説明 | 機能一覧を作る。分かる範囲で、その機能でできることを書く。 |
| 機能の分類や親子関係を示す機能一覧、メニュー、本文など | 根拠のある枝と深さまで機能ツリーを作る。親が分からない機能は一覧に残す。 |
| 機能・システム間の関係で、両端、種類、方向が分かる箇所 | 根拠のある辺を有向グラフとして記録する。 |
| 関係はあるが、相手・種類・方向のいずれかが不明な箇所 | 分かる事実を本文に残し、不明な点を「未確認」とする。その関係の辺は作らない。 |

## 機能ツリーを作る

- 資料が示す機能の親子関係を、入れ子の箇条書きで表す。枝の根拠を該当する項目や枝のまとまりに添える。資料の章立ては、それ自体が機能の分類を示していると確認できる場合に使う。
- 同じ機能が複数の分類に属すると明記されていれば、共通機能として一度説明し、各分類から参照する。主たる所属が分からないときは推測で親を選ばない。
- 親子関係が循環する場合は、同名の別機能を混同していないか、包含と依存を取り違えていないかを確かめる。食い違いが残る枝は未確認とする。機能ツリーからプログラムの配置を推定しない。

## 関係グラフを作る

- ノードには、資料で確認できる機能やシステムを使う。表では起点から終点へ向かう一行を一つの辺とし、関係の種類と根拠を記す。呼び出しは呼び出し元から呼び出し先、データ送信は送信元から受信先、依存は依存する側から依存される側へ向ける。受け渡すデータや適用条件が分かれば添える。
- 同名の機能やシステムが実際には別の要素なら、所属などで区別する。同じ要素だと確認できない場合は、統合せず未確認の点を残す。
- 双方向の連携は、両方向が成立する根拠があるときにそれぞれの辺を記す。資料によって同じ連携の方向が逆になっている場合は、適用条件や版の違いを確かめる。食い違いが残れば未確認とする。異なる種類の関係が同じ二つの要素を結ぶ場合や、根拠のある循環はそのまま残す。グラフは作業の実行順を表すものではない。

## 確認して保存する

- 資料間または既存文書との食い違いは、該当する記述と双方の参照元を記し、未確認とする。対立する情報から確定した枝や辺を追加しない。既存の記述は判断が済むまで保ち、その箇所から未確認の記録をたどれるようにする。利用者の判断が必要なら、影響する点から一問ずつ尋ねる。判断を待つ間も、根拠のある部分はまとめられる。
- 保存前に、各枝・各辺の根拠をたどれること、辺の両端と種類・方向を区別できること、未確認の点を本文で識別できることを確認する。
- 利用者の対応が必要な点は「確認・判断が必要な点」にまとめる。資料や調査で解消できる点は「未確認」とし、何を確認すればよいかを記す。方針を選ぶ必要がある点は「利用者の判断が必要」とし、何を決めるか、理由、影響する箇所を記す。親が分からない機能は一覧に残し、親が未確認であることを示す。根拠がそろうまで分類や関係は確定扱いにしない。

## 入力が部分的な例

機能一覧に「受注入力」と「受注照会」が載り、分類は書かれていないとする。連携表に「受注入力が在庫システムを呼び出す」とあり、別の項目には「会計システムと連携する」とだけある。この場合、機能は一覧で示す。グラフには「受注入力 → 在庫システム」の呼び出しを、連携表の位置とともに記す。会計連携は、確認できた事実を記し、種類・方向など、資料で特定できない点を本文に残す。
