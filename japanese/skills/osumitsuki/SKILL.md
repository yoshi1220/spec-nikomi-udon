# 基本設計書案の承認を記録する

1. 指定されたPBI、または現在の `feature/<変更名>` に対応する `specs/<変更名>/` を使う。対象が曖昧なら尋ねる。[お品書きの準備・移行手順](references/index.md) で現在の状態を確認する。`off` なら承認欄を作らずに終了する。`emergency` は理由とともに引き継ぐ。`approved` なら既存の記録を示して終了する。承認の記録へ進むのは `pending` の場合。
2. 対象の `shitagaki.md` について、実際に得た承認を記録する。承認日と承認者は、引数または呼び出しに続く本文から読み取る。たとえば `$osumitsuki --date 2026-11-20 --approver 設計責任者` と「11 月 20 日に設計責任者が承認」はどちらも使える。日付は年まで特定する。PR 方式では先にレビュー情報を読み、それでも不明な項目だけを一問ずつ尋ねる。後日記録する場合も、実際に承認された日を使う。
3. 案件の方式に応じて [approval.py](scripts/approval.py) を実行する。例の `<approval.py>` は導入したスクリプトのパス。対象を明示するときはサブコマンドの前に `--change specs/<変更名>` を付ける。
   - `operational` は案件の手続きで得た承認を `python3 <approval.py> approve --date YYYY-MM-DD --approver "承認者"` で保存する。
   - `pr` は `python3 <approval.py> approve` で現在の設計書案をPR先端と有効な承認時点の内容に照合する。指定されたPRは `--pr 番号` で渡す。省略時は対象ブランチの同一リポジトリの開いたPRが1件なら使う。GitHub CLIで検証できたレビューのログイン名と承認日（UTC）を使う。引数や本文に指定された日付・ログイン名があれば同じオプションで渡し、一致する承認を使う。他のPR連携では、対象PRの変更ファイルにこのPBIの設計書案が含まれ、有効な承認があることを確認する。PR先端と承認時点の両方でそのファイルのGit blob IDを取得する。`--verified-pr URL 先端のblob-ID 承認時のblob-ID` と、そのレビューの承認日・承認者を渡す。スクリプトが両方のIDを手元の設計案と照合する。構造変更案がある場合は、そのファイルについても両方の時点の blob ID を取得し、`--verified-plan 先端の計画blob-ID 承認時の計画blob-ID` で渡す。
4. 承認を確認できない場合や保存に失敗した場合は、該当箇所と必要な対応を伝える。保存できたら、`oshinagaki.md` が「承認済み」になり、承認日と承認者が記録されたことを確かめてから、`dandori` を案内する。
