# お品書きの準備と旧PBIの移行

[approval.py](../scripts/approval.py) は対象リポジトリで実行する。以下の操作は `python3 <approval.py> [--change specs/<変更名>] 操作` の形式で使う。

- 新規PBIでは `shikomi.md` の初回保存後に `init` を実行する。お品書きがなければ標準書式から作成し、設定が `operational` または `pr` のときだけ設計承認欄を追加する。他の成果物行を更新する際も、保存済みの承認欄を保持する。
- 設計・承認・計画に着手するときは `status` を読む。`off` は承認不要。`pending`、`approved`、`emergency` はそれぞれ承認待ち・承認済み・緊急対応を表す。読み取りエラーの場合は表示された箇所を直して再実行する。 中断後もロックが残る場合は、表示されたファイルのPIDを確認し、同じワークツリーを使う作業者も含めて処理が終了したことを確かめる。中断した処理の対象ファイルを点検してから、残ったロックを退避して再実行する。
- `uninitialized` は有効な設定で承認欄がまだない状態。対象PBIのお品書き、旧 `dandori.md` などの記録を照合する。対象PBIの緊急例外と省略理由を確認できた場合は `emergency --reason "元の理由"` で引き継ぐ。対象設計への承認、承認日、承認者を特定できれば `migrate --date YYYY-MM-DD --approver "承認者"` で取り込む。旧計画があることやPRの照会失敗後の続行だけでは承認の根拠にならない。判断材料が足りなければ `init` で設計を承認待ちにし、既存計画も保留にする。計画のタスクと作業結果は残る。`shitagaki` からの移行なら、そのまま設計を進める。通常の計画に進む前に、完成した設計案の承認を得て `osumitsuki` で記録する。
