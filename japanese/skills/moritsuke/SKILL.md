# 現行の基本設計からシステム全体の E2E テストを作る

1. リポジトリの `designs/specifications/` にある現行の基本設計を読み、利用者や連携先が確認できる一連の操作と期待結果を拾う。画面項目は対応する `*.screen-items.md` も参照する。`*.history.md` の変更理由や過去の PBI を根拠に、廃止済みの期待結果を復活させない。対象となる正本がなければ不足している仕様を伝える。既存のルート `e2e/` のシナリオ、テスト本体、共通ヘルパー、ランナー設定を確認する。
   構造管理を導入した案件では `structure/current.graphml` の現行ノードを `structure/index.json` で引き、対応する Markdown の節と、索引に記録された画面項目定義を使う。移行途中は、固定IDがまだない現行の基本設計書も対象に含める。`history/` や生成した階層表示はテストの入力から除外する。本文未整備の機能はその旨を報告する。
2. 現行仕様の参照箇所と、各テストが実際に行う操作・アサーションを対応づける。期待結果まで確認できる既存ケースと ID を引き継ぐ。追加された条件や機能間の流れが未検証なら、該当ケースを拡張するか、不足するケースを追加する。期待結果が変わったケースは正本に合わせて更新する。廃止が正本で確認できたケースは現行の実行対象から外す。仕様にもテストにも変更がない再実行で重複を作らない。
3. ルート `e2e/` にシナリオを記す。案件に既存の形式があればそれを使い、なければ `e2e/scenarios.md` にまとめる。シナリオごとに安定した ID、業務・機能名、正本のパスと節、前提・データ、手順、期待結果、必要な撮影場面、実行対象（テスト名・ファイル等）を対応づける。たとえば受注から出荷までを試すなら、同じ受注番号を使い、出荷後の照会でその受注が「出荷済み」と表示されることを確かめる。
4. [E2E の作成ルール](../e2e-authoring/SKILL.md) を読み、案件の E2E 方式で各シナリオを実施できるようにする。自動テストはルート `e2e/` に作成・更新し、テスト名から ID を選べるようにする。手動やブラウザ操作方式では、同じ ID で実施できる手順と観測点を用意する。
5. シナリオとともに、環境・データの準備、ルートの全件と指定 ID のみを選ぶコマンドまたは操作手順、証跡保存先の渡し方を記す。自動テストはランナーで実際に収集し、全件と指定 ID の対象がシナリオと一致することを確認する。追加・更新した ID と残る未検証箇所を伝え、[試食](../shishoku/SKILL.md) に引き継ぐ。
