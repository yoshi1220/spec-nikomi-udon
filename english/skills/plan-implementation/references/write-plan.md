# Write and verify the plan

## Record the execution list

- Keep the link to `shikomi.md`. Describe the affected areas, implementation patterns to follow, and code to reuse.
- In the implementation approach, link to `designs/repository-structure.md` as the basis for placement if it exists. If the structure document needs updating, include its path and task ID in “Planned changes” and identify the locations or responsibilities to record.
- Put “Planned changes” before the task list. Group the [identified paths](build-task-graph.md#identify-the-paths-to-change) by area and record the action (create, modify, or delete), what will change, and the related parent task IDs. If a path needs investigation, record what is known and identify the prerequisite investigation.
- List tasks in the order produced by the helper. For each task, record a checkbox, task ID, the result it provides, IDs and reasons for direct prerequisites, related acceptance criterion IDs, and a completion check. Use “None” for a task without prerequisites.
- When a task has several steps that can be verified separately, list them as checkboxes directly under the parent in execution order. Use `ST-<parent task number>-<sequence number>` for subtask IDs, starting the sequence at `01` for each parent. For example, subtasks of `T-01` are `ST-01-01` and `ST-01-02`. Give each subtask its own action and completion check. Use parent task IDs for dependencies and acceptance mappings. Each subtask inherits the parent prerequisites. Split only where the steps have distinct checks.
- Give each acceptance criterion one row with the required task IDs, test or manual setup and steps, and expected result. If existing behavior suffices, name the existing test or procedure. Mark new results as pending.
- Use the acceptance criteria, specification text, and existing design to identify behavior that changes and existing behavior the change could break. Choose setup and inputs that would produce an observable difference if that behavior broke, then record them alongside the expected result in the verification method. For example, for an inclusive upper limit, check acceptance at the limit and rejection at the next representable value. If a check has no direct acceptance criterion, record it in the related task’s completion check.
- Readers can follow the graph through the prerequisites in the task list. A separate dependency document is unnecessary.

## Update an existing plan

At the start of replanning, save the first-line marker as `<!-- dandori-plan: pending -->` while preserving the plan body and results. Insert the marker on the first line of a legacy plan without one. If the index exists, mark the implementation plan “On hold” while checking prerequisites. If an unresolved prerequisite interrupts replanning, leave the plan on hold and explain what blocks execution.

Update “Planned changes” along with the task list. If the earlier plan has no such section, add it using the specification, code, and task list.

Compare it with the previous plan. Preserve IDs that follow the format and valid evidence for unchanged subtasks. If correcting the format changes a subtask ID, update its references and link its evidence to the new ID. Give each added subtask an unused suffix within its parent and leave it unchecked. If an older plan recorded only parent completion, mark a subtask complete only when the prior evidence meets that subtask's completion check. Keep completion and verification evidence where the work, completion checks, and underlying evidence remain valid. Reordering alone does not change completion. When changes affect a task or its prerequisite results, follow the edges to determine which downstream checks and results remain valid. Reopen affected tasks and mark affected acceptance criteria for re-verification with the reason. If retaining older evidence for reference, make the need for re-verification visible.

## Check the plan before and after saving

1. “Planned changes” comes before the task list and covers the directories to create and files to create, modify, or delete. Check each row’s path and action against the specification, repository layout, and the work described by its parent task. If the structure document needs updating, check that its task depends on the relevant implementation and verification work.
2. Parent tasks follow the helper's output and appear exactly once. Their prerequisite IDs must be unique, match their direct prerequisites in the graph, and refer to earlier parent tasks. Check that subtasks appear directly under their parent in execution order. Each subtask ID must follow `ST-<parent task number>-<sequence number>`, match the actual parent task number, and be unique. A parent with unchecked subtasks remains unchecked.
3. Every criterion in `shikomi.md` has a concrete verification method and expected result. Check that the plan, including task completion checks, pairs inputs with expected results that reveal breaks in the behavior under test. All required tasks are present, and the IDs in the task list and verification table agree.
4. Check that unit-level rules map to tests and the plan adds or updates unit-test code before implementing new or changed behavior. If no unit-level behavior is in scope, check the recorded reason. Check the project's execution and measurement method and scope. Every task supports agreed behavior, a constraint, or verification. For preparation without a direct acceptance criterion, identify the downstream task or constraint that requires it. Check that the plan stays within the specification's scope.
5. If the project workflow includes E2E testing (including `pr` and `operational` design approval), or the PBI already has a basic design draft or `e2e.md`, [plan E2E tests](plan-e2e.md) and link to `e2e.md` from `dandori.md`. Save the plan with the marker still pending. Re-read it and check items 1–4. Once the checks pass and the prerequisites for execution are met, run [approval.py](../../record-design-approval/scripts/approval.py) with `finish-plan`. It reads the current approval state and sets the first-line marker to ready under the same lock used by `redraft`. If approval is pending, leave the plan on hold and resume after approval.
6. If the deliverable index exists, link to the saved `dandori.md`. Mark it “Complete” after `finish-plan` succeeds. Use “On hold” when approval or another prerequisite is outstanding, and “In progress” while writing or checking the plan. Report the plan's location and whether it is ready to execute.
