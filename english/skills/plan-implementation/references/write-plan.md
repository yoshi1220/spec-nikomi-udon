# Write and verify the plan

## Record the execution list

- Keep the link to `shikomi.md`. Describe the affected areas, implementation patterns to follow, and code to reuse.
- List tasks in the order produced by the helper. For each task, record a checkbox, task ID, the result it provides, IDs and reasons for direct prerequisites, related acceptance criterion IDs, and a completion check. Use “None” for a task without prerequisites.
- When a task has several steps that can be verified separately, list them as checkboxes directly under the parent in execution order. Append sequential suffixes starting at `-01` to the parent ID, for example `T-01-01`. Give each subtask its own action and completion check. Use parent task IDs for dependencies and acceptance mappings. Each subtask inherits the parent prerequisites. Split only where the steps have distinct checks.
- Give each acceptance criterion one row with the required task IDs, test or manual setup and steps, and expected result. If existing behavior suffices, name the existing test or procedure. Mark new results as pending.
- Use the acceptance criteria, specification text, and existing design to identify behavior that changes and existing behavior the change could break. Choose setup and inputs that would produce an observable difference if that behavior broke, then record them alongside the expected result in the verification method. For example, for an inclusive upper limit, check acceptance at the limit and rejection at the next representable value. If a check has no direct acceptance criterion, record it in the related task’s completion check.
- Readers can follow the graph through the prerequisites in the task list. A separate dependency document is unnecessary.

## Update an existing plan

At the start of replanning, save the first-line marker as `<!-- dandori-plan: pending -->` while preserving the plan body and results. Insert the marker on the first line of a legacy plan without one. If the index exists, mark the implementation plan “On hold” while checking prerequisites. If an unresolved prerequisite interrupts replanning, leave the plan on hold and explain what blocks execution.

Compare it with the previous plan. Preserve IDs and valid evidence for unchanged subtasks. Give each added subtask an unused suffix within its parent and leave it unchecked. If an older plan recorded only parent completion, mark a subtask complete only when the prior evidence meets that subtask's completion check. Keep completion and verification evidence where the work, completion checks, and underlying evidence remain valid. Reordering alone does not change completion. When changes affect a task or its prerequisite results, follow the edges to determine which downstream checks and results remain valid. Reopen affected tasks and mark affected acceptance criteria for re-verification with the reason. If retaining older evidence for reference, make the need for re-verification visible.

## Check the plan before and after saving

1. Parent tasks follow the helper's output and appear exactly once. Their prerequisite IDs must be unique, match their direct prerequisites in the graph, and refer to earlier parent tasks. Check that each subtask sits directly under its parent, has a unique ID prefixed with the parent ID, and appears in execution order. A parent with unchecked subtasks remains unchecked.
2. Every criterion in `shikomi.md` has a concrete verification method and expected result. Check that the plan, including task completion checks, pairs inputs with expected results that reveal breaks in the behavior under test. All required tasks are present, and the IDs in the task list and verification table agree.
3. Check that unit-level rules map to tests and the plan adds or updates unit-test code before implementing new or changed behavior. If no unit-level behavior is in scope, check the recorded reason. Check the project's execution and measurement method and scope. Every task supports agreed behavior, a constraint, or verification. For preparation without a direct acceptance criterion, identify the downstream task or constraint that requires it. Check that the plan stays within the specification's scope.
4. If the project workflow includes E2E testing (including `pr` and `operational` design approval), or the PBI already has a basic design draft or `e2e.md`, [plan E2E tests](plan-e2e.md) and link to `e2e.md` from `dandori.md`. Save the plan with the marker still pending. Re-read it and check items 1–3. Once the checks pass, run [approval.py](../../record-design-approval/scripts/approval.py) with `finish-plan`. It reads the current approval state and sets the first-line marker to ready under the same lock used by `redraft`. If approval is pending, leave the plan on hold and resume after approval.
5. If the deliverable index exists, link to the saved `dandori.md`. Mark it “Complete” after `finish-plan` succeeds. Use “On hold” when approval or another prerequisite is outstanding, and “In progress” while writing or checking the plan. Report the plan's location and whether it is ready to execute.
