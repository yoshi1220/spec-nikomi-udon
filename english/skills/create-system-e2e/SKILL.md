# Create system E2E tests from current specifications

1. Read the current basic designs in `designs/specifications/`. Identify workflows and outcomes observable by users or connected systems. Use the corresponding `*.screen-items.md` for screen fields where available. A change reason in `*.history.md` or a past PBI may describe retired behavior. Derive current expectations from the current design. If a relevant specification is missing, report what is needed. Inspect existing scenarios, tests, helpers, and runner configuration for the root `e2e/`.
   For a structured project, resolve current nodes in `structure/current.graphml` through `structure/index.json`. Use the indicated Markdown section and any screen item path recorded for it. During migration, also include current basic designs that still lack fixed IDs. Exclude `history/` and generated hierarchy summaries from test inputs. Report a confirmed function with missing specification text.
   Treat `planned` nodes as future design work and exclude them from tests of current behavior.
2. Map each specified outcome to the actions and assertions in existing tests. Preserve cases and IDs that already verify the outcome. Extend a case or add a missing one when a new condition or cross-feature workflow lacks coverage. Update affected expectations when the specification changes. Exclude retired cases from the active suite when the current specification confirms that the behavior was retired. Repeating this comparison against unchanged specifications and tests should produce no duplicates.
3. Record scenarios under the root `e2e/`. Use the project's existing scenario format or start with `e2e/scenarios.md`. Associate each stable ID with its workflow or feature, specification path and section, prerequisites and data, steps, expected results, requested capture checkpoints, and runnable test name or file. For example, follow the same order number through shipping and verify its “Shipped” status in the order view.
   If a scenario depends on a particular service, name it and its environment in the prerequisites. Use the relevant section of `designs/technical-context.md` when available.
4. Read the [E2E authoring rules](../e2e-authoring/SKILL.md) and prepare each scenario for the project's E2E method. Create or update automated tests under the root `e2e/` and make their IDs selectable through the test names. For manual or agent-driven browser tests, supply steps and observable checks for the same IDs.
5. With the scenarios, record environment and data setup, commands or steps to select the full root suite and individual IDs, and how to pass the evidence directory. For automated tests, use runner collection to verify the full suite and an ID selection against the scenarios. Report the IDs added or updated and remaining coverage gaps, then hand off to [execute-system-e2e](../execute-system-e2e/SKILL.md).
