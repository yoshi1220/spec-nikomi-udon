# Migrate basic design documents

1. Identify the shared branch revision and the project template the user intends to adopt. By default, select the per-function basic designs under `designs/specifications/`. Exclude revision histories, screen item definitions, and other documents. Ask about ambiguous documents. If the user specifies a scope or groups by business area or function, list the documents in each requested group.
2. Prepare one dedicated documentation PR per group. By default, put all selected documents in one PR. Work on a dedicated branch based on the shared revision and keep the existing document paths. If unrelated edits are present, use a separate worktree before writing and carry over the intended template and guidance. Resolve the [project basic design template and writing guidance](../shitagaki/references/basic-design-format.md) in the migration worktree. If the shared template or guidance changes are needed for review, show them as related changes. Include them once or make them a shared prerequisite to avoid conflicts across PRs.
3. Carry forward each document's business rules, behavior, evidence, unverified findings, and manual edits into the new fields. Mark information absent from the original as unverified. For unclear destinations, show the original and candidate fields and ask the user. Continue drafting documents whose destinations are clear. On interruption, report the branch, source revision, template digest, scope, decisions, and pending questions. On resumption, compare them with the current diff. Recheck affected documents if the originals or template changed.
   In structured projects compare the current index with the selected documents so legacy designs awaiting migration are also covered. Preserve fixed-ID markers with their headings and leave `structure/` and `history/` out of template conversion. Use the [documentation-only structure update](../osameru/references/structure.md) for indexed designs in each reviewed group to refresh their locations and node revisions.
4. Once every document in a group is ready, compare the source and result. Verify that design meaning and applicable content survived, and that the diff contains only the intended documentation. Identify documents already in the new format with no diff. Prepare the PR description with the scope, migration diff, main field mappings, and information still needed for newly added fields. If the shared branch has newer edits to the selected documents, reconcile them and review again. The shared canonical designs update on merge. Send or merge the PR when requested by the user.
